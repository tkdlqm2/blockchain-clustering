# 01. 기능 명세서 (Functional Specification)

> 이 시스템이 **무엇을** 하는지 정의한다. 요구사항은 검증 가능한 단위로 기술하며, 각 요구사항에는 식별자(FR-n / NFR-n)를 부여해 05의 인수 기준과 연결한다.

---

## 1. 범위 (Scope)

BalanceDelta를 입력으로 받아, 주소를 엔티티로 클러스터링하고, 병합 근거·신뢰도·라벨을 관리하며, 그 결과를 조회로 제공하는 **백엔드 시스템**을 만든다.

### 1.1 만들 것
- BalanceDelta 수집·적재 (인덱서로부터).
- 전처리: 허브 탐지, 협업 트랜잭션(CoinJoin) 탐지, dust 표시.
- 클러스터링 휴리스틱: 공통 입력, sweep(집금), 잔돈(보수적), (계정 체인) 자금융통·행동.
- 병합 근거 로그(append-only)와 그로부터 파생되는 클러스터 멤버십.
- 라벨 관리(출처·신뢰도·신선도).
- 증분 갱신과 reorg 롤백.
- 조회 API: 주소→엔티티, 엔티티 멤버십, 병합 근거, 라벨, 엔티티 단위 흐름.

### 1.2 안 만들 것 (비범위, Non-goals)
- **블록 인덱싱 자체**: BalanceDelta 생산은 별도 인덱서의 책임. 이 시스템은 그 출력을 소비만 한다.
- **상위 응용 서비스**: 리스크 스코어링 엔진, 수사 대시보드, 트레이딩 인텔리전스 UI 등은 이 시스템의 **소비자**이지 구성요소가 아니다. 단, 이들이 필요로 하는 조회 표면(엔티티·흐름·라벨)은 제공한다(§5).
- **신원 확인(KYC)·실명 매핑**: 라벨은 "이 엔티티는 거래소 X"까지이며, 개인 신원 특정은 범위 밖.
- **가격·환율·회계 계산.**
- **프라이버시 공격 도구화**: 개별 사용자의 프라이버시를 표적 해제하는 기능은 설계 목적이 아니다. (윤리·규제 고려는 §6.)

---

## 2. 액터 (Actors)

- **인덱서(상류 시스템)**: BalanceDelta를 공급한다.
- **분석가/운영자**: 라벨 시드를 주입(known-deposit 결과 등)하고, 오탐을 정정하며, 임계치를 조정한다.
- **소비 서비스**: 조회 API를 호출하는 상위 애플리케이션.

## 3. 기능 요구사항 (Functional Requirements)

### 3.1 데이터 수집
- **FR-1** 시스템은 인덱서로부터 BalanceDelta를 수집해 적재한다. 입력은 스트리밍(신규 블록) 또는 배치(백필) 두 모드를 지원한다.
- **FR-2** 각 BalanceDelta는 `source_block_hash`와 `block_height`를 보존해야 한다(reorg 롤백 근거).
- **FR-3** 동일 BalanceDelta의 중복 수집은 멱등적으로 처리한다(재적재 시 상태 불변).

### 3.2 전처리 (병합 이전 오염 차단)
- **FR-4** 시스템은 허브 후보 주소를 탐지해 표시한다. 근거는 (a) known 라벨, (b) 행동 지표(상대방 수·빈도·sweep 수렴). 탐지에도 confidence를 부여한다.
- **FR-5** 시스템은 협업 트랜잭션(CoinJoin류)을 탐지해 표시하고, 공통 입력 휴리스틱 적용 대상에서 제외한다. 단, "이 자금이 협업 트랜잭션을 거쳤다"는 사실은 신호로 보존한다.
- **FR-6** 시스템은 dust 유입을 표시하고, dust 공유만을 근거로 한 병합을 차단한다.
- **FR-7** (요구) 전처리는 클러스터링 휴리스틱보다 **먼저** 수행되어야 한다. 순서 위반은 결함으로 간주한다.

### 3.3 클러스터링 휴리스틱
- **FR-8** **공통 입력(UTXO)**: 같은 트랜잭션에서 함께 지출된(음수 delta) 주소들을 하나의 클러스터로 병합한다. 허브·협업 트랜잭션은 제외한다(FR-5, FR-7).
- **FR-9** **sweep/입금 주소(거래소)**: known-deposit 시드로 확보한 집금 목적지를 앵커로, 같은 목적지로 집금되는 입금 주소들을 해당 거래소 엔티티로 병합한다. 입금을 **보낸** 원천 주소(사용자 지갑)는 병합하지 않는다.
- **FR-10** **잔돈(change)**: 잔돈 후보를 추정해 병합하되, 낮은 confidence로만 부여하고 단독 근거로 확정하지 않는다.
- **FR-11** **(계정 체인)** 공통 입력 대신 자금융통(funding)·배포자(deployer)·행동 패턴 휴리스틱을 적용한다. 이들은 별도 트랙으로 구성하며, UTXO 휴리스틱과 혼용하지 않는다.
- **FR-12** 각 휴리스틱은 병합을 직접 수행하지 않고 **병합 후보(MergeEvidence candidate)** 를 생성한다. 실제 병합은 병합 엔진이 근거를 기록하며 수행한다(FR-14).

### 3.4 병합·근거·신뢰도
- **FR-13** 모든 병합은 append-only **병합 근거 로그**에 기록된다. 각 레코드는 최소 `(chain, address_a, address_b, heuristic, source_txid, source_block_hash, confidence, created_at)` 를 포함한다.
- **FR-14** 클러스터 멤버십은 병합 근거 로그를 재생(replay)해 산출되는 파생물이다. 근거 로그가 진실의 원천이며, 멤버십 저장소는 캐시로 취급한다.
- **FR-15** 시스템은 임의의 두 주소가 같은 클러스터인지(`same_cluster`), 특정 주소의 클러스터 소속(`cluster_of`)을 조회할 수 있다.
- **FR-16** 각 병합에 confidence를 부여하고, 조회 시 신뢰도 임계치로 클러스터 뷰를 다르게 산출할 수 있다(예: `min_confidence` 파라미터).
- **FR-17** 병합 근거는 독립적 복수 근거의 결합 시 신뢰도를 조정할 수 있어야 한다(교차 검증). 결합 규칙은 03 §7에 따른다.

### 3.5 라벨링
- **FR-18** 시스템은 클러스터 또는 주소에 라벨을 부여한다. 각 라벨은 `(target, label, category, source, source_confidence, collected_at, last_verified_at, status)` 를 가진다.
- **FR-19** 라벨은 출처 등급(직접검증 > 공식공시 > 크라우드소싱)에 따라 신뢰도가 차등된다.
- **FR-20** 시스템은 라벨 신선도를 관리한다. 일정 기간 미검증 라벨은 confidence를 감쇠하거나 재검증 대상으로 표시한다.
- **FR-21** 한 클러스터에 상충하는 라벨이 부여되면 자동 확정하지 않고 충돌로 표시한다.

### 3.6 증분·롤백
- **FR-22** 신규 BalanceDelta는 전체 재계산 없이 증분으로 반영한다. 새 관계로 두 기존 클러스터가 합쳐질 수 있다.
- **FR-23** reorg가 통지/감지되면, 롤백된 `source_block_hash`를 근거로 가진 병합 레코드를 무효화하고, 남은 근거를 재생해 멤버십을 재산출한다.
- **FR-24** 운영자는 특정 병합 근거를 수동 무효화(오탐 정정)할 수 있으며, 그 즉시 멤버십에 반영된다(재생).

### 3.7 운영·정정
- **FR-25** 운영자는 라벨 시드와 허브 지정을 주입/수정할 수 있다.
- **FR-26** 시스템은 병합/라벨의 감사 추적(누가·언제·무엇을·왜)을 남긴다.

## 4. 비기능 요구사항 (Non-functional Requirements)

- **NFR-1 정확성 우선**: 오탐(무관 주소의 오병합)을 정탐 누락보다 강하게 회피한다. 기본 파라미터는 보수적으로 설정한다.
- **NFR-2 되돌림 가능성**: 임의 병합을 근거 무효화만으로 되돌릴 수 있어야 한다(전체 재계산 불요).
- **NFR-3 멱등성**: 동일 입력의 재처리는 동일 결과를 낳는다.
- **NFR-4 확장성**: 주소 수는 수억 규모를 상정한다. Union-Find와 근거 로그는 이 규모에서 동작해야 한다(메모리 내 또는 외부화 전략은 스택 선택 시 결정).
- **NFR-5 감사 가능성**: 모든 클러스터 소속은 "왜 이렇게 묶였는가"를 근거 레코드로 설명할 수 있어야 한다.
- **NFR-6 관찰 가능성**: supernode 발생, 병합률, 오탐 정정 빈도, 라벨 신선도 등을 지표로 노출한다.
- **NFR-7 스택 비종속성**: 로직·모델·인터페이스는 특정 스택 가정 없이 구현 가능해야 한다.

## 5. 서비스 표면 (조회 API — 논리 계약)

물리 프로토콜(REST/gRPC/GraphQL)은 구현자가 정한다. 아래는 **논리적 조회 능력**이다.

- `cluster_of(chain, address, min_confidence?) → cluster_id, confidence`
- `members_of(cluster_id, min_confidence?) → [address...]` (대용량 시 페이지네이션)
- `same_cluster(chain, addr_a, addr_b, min_confidence?) → bool, confidence`
- `evidence_of(cluster_id | address_pair) → [merge_evidence...]` (감사·근거 제시)
- `labels_of(cluster_id | address) → [label...]`
- `entity_flow(cluster_id, direction, window) → [엔티티 단위 자금 흐름 엣지...]` (주소 그래프를 엔티티 그래프로 접은 흐름)
- `hub_status(chain, address) → hub_flag, hub_type?, confidence`

> `entity_flow`는 상위 추적 서비스가 올라타는 핵심 추상화다(엔티티 그래프). 흐름 자체의 응용(수사·리스크)은 소비자의 몫이다.

## 6. 윤리·규제 고려 (설계 제약)

- 라벨·클러스터 결과는 **확률적 추정**이며, 조회 응답은 confidence를 반드시 동반한다(단정 금지).
- 잘못된 지목의 실제 피해(계정 동결·명예)를 감안해, 오탐 정정 경로(FR-24)를 1급 기능으로 둔다.
- 개별 사용자 표적 해제를 조장하는 기능은 명세하지 않는다. 시스템의 정당한 용도(컴플라이언스·수사·분석)를 전제로 한다.
