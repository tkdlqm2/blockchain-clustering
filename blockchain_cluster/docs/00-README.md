# 온체인 주소 클러스터링 시스템 — 구현 스펙 패키지

> **이 패키지의 목적**: 구현자(Claude Sonnet 5 또는 사람)가 추가 설계 판단을 최소화하고 온체인 주소 클러스터링 시스템을 완성도 높게 구현할 수 있도록, 요구사항·논리 데이터 모델·알고리즘·아키텍처·구현 계획·테스트를 명세한다.
>
> **기술 스택 비종속**: 언어·DB·프레임워크·인프라는 **구현자가 선택한다.** 따라서 이 패키지의 모든 내용은 특정 스택에 묶이지 않는 **논리 수준**으로 기술한다. 데이터 모델은 물리 DDL이 아니라 논리 스키마로, 로직은 언어 무관 의사코드로, 컴포넌트는 프레임워크가 아니라 인터페이스 계약으로 제시한다. 스택이 정해지면 각 문서의 논리 명세를 그 스택으로 사상(map)하면 된다.

## 시스템 한 줄 정의

> 인덱서가 생산한 **자산 이동 기록(BalanceDelta)** 을 입력으로, 여러 주소를 같은 통제 주체(엔티티)로 **되돌릴 수 있게** 묶고, 각 병합에 **근거와 신뢰도**를 부여하며, 그 위에 라벨·조회를 제공하는 시스템.

## 상위 컨텍스트 — 이 시스템의 위치

```
[블록체인 노드]
      │
      ▼
[인덱서]  ──생산──▶  BalanceDelta (txid, address, amount±, ...)   ← 이 시스템의 입력
      │                        │
      │                        ▼
      │              ┌───────────────────────────┐
      │              │  클러스터링 시스템 (이 패키지)  │
      │              │  전처리 → 휴리스틱 → 병합    │
      │              │  → 라벨링 → 조회            │
      │              └───────────────────────────┘
      │                        │
      ▼                        ▼
[조회/서비스]  ◀──  엔티티 그래프 (주소→엔티티, 흐름, 라벨)
```

- **입력**: BalanceDelta 스트림. 스키마 상세는 별도 인덱서 문서(외부)를 참조하되, 이 패키지가 의존하는 최소 필드는 02-data-model §1에 재기술한다.
- **출력**: 엔티티(클러스터) 정의, 주소→엔티티 매핑, 병합 근거, 라벨. 이를 활용한 상위 서비스(리스크 스코어링·추적·인텔리전스)는 이 시스템의 **소비자**이며 이 패키지의 범위 밖이다(01 §비범위).

## 핵심 설계 원칙 (모든 문서를 관통)

1. **근거가 진실의 원천이다.** 클러스터 결과가 아니라 **병합 근거 로그(merge_evidence)** 가 진실의 원천이며, 클러스터 멤버십은 그로부터 파생되는 캐시다. 이래야 오탐 정정·reorg 롤백이 가능하다.
2. **되돌릴 수 있게 합친다.** 병합은 monotonic(자연히 풀리지 않음)이므로, 모든 병합은 `source_block_hash`까지 특정한 근거와 함께 기록해 재생(replay)·롤백이 가능해야 한다.
3. **오염을 먼저 막는다.** 허브·협업 트랜잭션·dust를 병합 **이전** 단계에서 제거/표시한다. 순서가 성능보다 중요하다.
4. **확정하지 말고 점수를 매긴다.** 모든 병합에 confidence를 부여하고, 조회는 신뢰도 임계치로 뷰를 분리한다.
5. **체인 모델에 맞춘다.** UTXO(공통 입력 주력)와 계정(자금융통·행동 주력)의 휴리스틱을 분리한다.

> 이 원칙들의 근거와 실무 함정은 자매 문서 **온체인 클러스터링 플레이북**(별도 파일)에 상세하다. 본 패키지는 그 원칙을 "구현 가능한 스펙"으로 구체화한 것이며, 개념 배경이 필요하면 플레이북을 함께 참조한다.

## 용어집 (Glossary)

- **주소(address)**: 자금이 오가는 최소 식별자. 체인별 문자열.
- **엔티티(entity) / 클러스터(cluster)**: 같은 주체가 통제한다고 추정되는 주소들의 묶음. 이 문서에서 두 용어는 동의어로 쓰되, "클러스터"는 알고리즘 산출물, "엔티티"는 그에 정체성(라벨)이 붙은 상태를 강조할 때 쓴다.
- **BalanceDelta**: 인덱서가 생산하는 부호 있는 자산 이동 원자 단위. `(chain, txid, address, amount±, kind, ...)`.
- **휴리스틱(heuristic)**: 두 주소가 같은 주체 소유임을 추정하는 규칙(공통 입력, sweep, 잔돈 등).
- **병합 근거(merge_evidence)**: 어떤 트랜잭션의 어떤 휴리스틱으로 두 주소를 합쳤는지에 대한 append-only 기록. **진실의 원천.**
- **Union-Find (DSU)**: 병합·소속판정을 상수 시간에 처리하는 자료구조. 여기서는 merge_evidence를 재생해 만든 **파생 캐시**.
- **허브(hub) / supernode**: 거래소·믹서·브릿지처럼 무관한 다수 주체의 자금이 통과하는 노드. 병합에서 제외/차단 대상.
- **sweep(집금, collection)**: 거래소가 다수 입금 주소의 자금을 집금 주소로 쓸어담는 자동·반복 패턴. 입금 주소를 거래소 엔티티로 묶는 근거.
- **confidence**: 병합·라벨의 신뢰도 점수(0~1).
- **reorg**: 저장했던 블록 일부가 교체되어 무효화되는 사건. 관련 병합 근거를 무효화·재생해야 한다.

## Sonnet(구현자)를 위한 사용 지침

1. **읽는 순서를 지켜라**: 01(무엇) → 02(데이터) → 03(로직) → 04(조립) → 05(순서·검증).
2. **03의 의사코드를 스택 언어로 옮길 때 알고리즘 구조를 바꾸지 마라.** 특히 파이프라인 순서(전처리→병합)와 "merge_evidence = 진실의 원천, Union-Find = 파생" 관계는 정확성의 근간이다.
3. **모호하면 보수적으로.** 병합할지 말지 애매하면 낮은 confidence를 부여하거나 병합하지 않는다. 오탐 1건이 정탐 누락 1건보다 비싸다(오탐은 전파된다).
4. **05의 인수 기준을 구현 완료의 정의(Definition of Done)로 삼아라.** 특히 "허브 제외로 supernode 미발생", "reorg 롤백 정확", "재처리 멱등"은 반드시 통과해야 한다.
5. **스택 선택 시 요구 능력**: (a) append-only 로그의 대량 쓰기/집계, (b) 수억 원소 Union-Find(메모리 또는 외부화), (c) 주소·txid 기준 인덱싱 조회. 이 세 가지를 만족하면 스택은 자유다.
