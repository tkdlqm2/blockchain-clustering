# api_review — API 설계·계약 리뷰 렌즈

점검 대상: $ARGUMENTS

> 이 커맨드는 **이 프로젝트가 외부(클라이언트/파트너/프론트엔드)에 제공하는 API의 계약 안정성**만 본다.
> 우리가 남을 호출할 때의 신뢰성은 `comm_review`, 예외가 터졌을 때의 상태코드 매핑은 `error_review`, 입력 검증 자체의 존재 여부는 `validation_review`, 도메인 엔티티 노출이 계층 위반인지는 `arch_review`가 각자의 각도에서 본다 — 여기서는 "이 계약이 지금도, 나중에도 클라이언트를 깨지 않는가"만 본다.
> "먼저 이 프로젝트가 제공하는 API 표면을 찾고(STEP 1) → 발견된 종류에만 해당 항목을 적용(STEP 2)"하는 순서를 반드시 지킨다.
> 사용법: `api_review [선택: 경로 또는 엔드포인트/스키마 이름]`
> - 인자 없음 → 프로젝트 전체 스캔
> - 인자 있음 → 해당 경로/엔드포인트로 범위 한정

---

## 범위 (Scope)

- **대상**: 이 프로젝트가 외부에 노출하는 API 표면 — REST/HTTP 엔드포인트, GraphQL 스키마, gRPC 서비스 정의(제공자 입장)의 버전 관리, 하위 호환성(필드 추가/삭제/타입 변경), 페이지네이션 방식, 응답 스키마 일관성, HTTP/gRPC 상태코드의 설계상 시맨틱, 응답에 도메인 엔티티/ORM 객체 직접 노출.
- **제외**: 이 프로젝트가 남을 호출할 때의 재시도·타임아웃·회복력(→ `comm_review`), 예외 발생 시 에러→상태코드 매핑 일관성(→ `error_review`, 여기서는 "설계된 상태코드 체계"만 보고 "예외가 실제로 어떤 코드로 떨어지는지"는 다루지 않는다), 입력 검증 로직의 존재·이중 방어 여부(→ `validation_review`), 도메인 엔티티 노출이 계층 의존성 위반인지 자체(→ `arch_review`, 여기서는 "하위 호환성 리스크" 관점에서만 지적), 이 엔드포인트에 인증/인가가 걸려 있는지·IDOR 여부(→ `security_review`, 여기서는 응답 스키마/노출 필드만 보고 접근 통제 자체는 다루지 않는다), DB/동시성/정합성(→ `db_review`/`concurrency_review`/`consistency_review`). 이 항목이 나오면 "범위 밖, 해당 커맨드로"라고만 표시하고 리뷰하지 않는다.

---

## STEP 1 — 대상 인벤토리 (Discovery) · 반드시 먼저

코드베이스를 스캔해 **실제로 존재하는 API 표면만** 목록화한다. 없는 것은 리뷰하지 않는다.

탐지 신호:

| 종류 | 탐지 신호(예시) |
|------|----------------|
| REST/HTTP | 라우터/컨트롤러 정의(`@RestController`, Express/Gin/Fiber 라우트, FastAPI `@app.get` 등), OpenAPI/Swagger 스펙 파일 |
| GraphQL | `.graphql`/`.gql` 스키마 파일, resolver 정의 |
| gRPC (제공자) | `*.proto` 중 이 프로젝트가 서버로 구현하는 서비스, 생성된 서버 스텁 구현체 |
| 버저닝 흔적 | URL의 `/v1/`, `/v2/`, 헤더 버전, proto 패키지 버전(`v1`, `v2`) |
| 응답 직렬화 | 컨트롤러/리졸버가 반환하는 타입이 별도 DTO/Serializer인지, 도메인 엔티티/ORM 모델 그대로인지 |
| 페이지네이션 | `limit`/`offset` 파라미터, cursor 파라미터, 응답의 `total`/`nextCursor` 등 메타데이터 |
| 상태코드 사용 | 컨트롤러의 상태코드 리터럴(200/201/204/4xx/5xx)과 어떤 동작에 쓰였는지 |

**STEP 1 출력**: 발견된 API 표면의 표를 먼저 제시한다.

| # | 엔드포인트/스키마 | 종류(REST/GraphQL/gRPC) | 버전 표시 여부 | 진입 파일:라인 |
|---|-------------------|--------------------------|----------------|-----------------|

- 하나도 못 찾으면: 리뷰를 만들지 말고 "외부 제공 API를 찾지 못함. 있는데 못 찾았다면 경로를 알려달라"고 **한 번만** 묻는다.
- 내부 전용인지 외부 공개인지 애매한 엔드포인트만 모아서 함께 확인한다.

## STEP 2 — 대상별 점검 (발견된 종류에만 적용)

각 API 표면에 대해, **그 종류에 해당하는 항목만** 본다. 프로젝트에 없는 프로토콜(GraphQL 없는데 GraphQL 스키마 진화 지적 등)의 항목은 만들어내지 않는다.

### A. 공통 (모든 API 표면에 적용)
- **버전 관리**: 이 API에 버저닝 전략(URL/헤더/네임스페이스)이 있는가. 없다면 향후 breaking change를 어떻게 낼 계획인지 확인 가능한가.
- **하위 호환**: 필드 삭제·타입 변경·필수 필드 추가처럼 기존 클라이언트를 깨는 변경이 버전업 없이 이루어지는가. 신규 필드는 optional로 추가되는가.
- **응답 스키마 일관성**: 유사한 리소스의 필드명·형식(날짜 포맷, null vs 필드 누락, 페이지네이션 구조)이 엔드포인트마다 다르지 않은가.
- **상태코드 시맨틱**: 생성 시 201, 본문 없는 성공에 204, 클라이언트/서버 오류가 4xx/5xx로 구분되는가 — 정상 응답 200 안에 에러를 담아 보내는 등 설계 자체가 어긋난 경우만 지적(예외 매핑의 일관성 자체는 `error_review` 소관).
- **도메인 엔티티 직접 노출**: 응답이 ORM 엔티티/도메인 객체를 그대로 직렬화하는가 — 내부 필드·연관관계·민감 정보 노출 위험 + 도메인 모델 변경이 곧 API breaking change가 되는 결합 위험.

### B. 페이지네이션 (페이지네이션이 있을 때만)
- offset 기반인지 cursor 기반인지 — 대용량 목록에 offset을 쓰면 조회 중 데이터가 추가/삭제될 때 항목이 중복되거나 누락될 수 있는 **계약상** 위험(성능 저하 자체는 `db_review` 소관).
- 클라이언트가 다음 페이지 존재 여부/전체 개수를 판단할 메타데이터가 응답에 있는가.

### C. GraphQL (GraphQL 스키마가 있을 때만)
- deprecated 필드에 `@deprecated` 지시어와 사유가 명시되는가.
- 필드 삭제·타입 변경이 breaking change로 관리되는가.
- N+1을 유발하기 쉬운 구조(중첩 리스트 필드)인지(성능 자체는 `db_review`, 여기서는 스키마 설계 문제로만 언급).

### D. gRPC 계약 (제공자로 구현한 proto가 있을 때만)
- 필드 번호 재사용 금지, 삭제 시 `reserved` 처리 등 계약 관리 프로세스가 지켜지는가(런타임 파싱 안전성 자체는 `comm_review` C 섹션 소관, 여기서는 "계약을 깨는 변경이 관리되는가"만).

### E. 문서화 (API 스펙 문서가 있을 때만)
- OpenAPI/스키마 문서가 실제 구현과 어긋나 있지 않은가(눈에 띄는 불일치가 있으면 지적, 전수 비교는 하지 않는다).

## STEP 3 — 출력 포맷 (일정하게)

각 발견은 아래 형식으로. 심각도 순(Critical→Low)으로 정렬한다.

```
[심각도] <한 줄 요약>
  대상 : <엔드포인트/스키마 이름>
  위치 : <파일:라인>
  근거 : <왜 문제인가 — STEP 2의 어떤 항목 위반인지>
  수정안: <구체적 조치 — 버전 분리/DTO 도입/스키마 수정 등>
```

**심각도 기준**
- `Critical`: 버전업 없이 배포된 breaking change(필드 삭제/타입 변경), 도메인 엔티티 노출로 민감 정보 유출.
- `High`: 응답 스키마 불일치로 클라이언트 파싱 실패 위험, offset 페이지네이션의 데이터 중복/누락.
- `Medium`: 상태코드 시맨틱 오용, deprecated 필드 사유 미명시.
- `Low`: 문서와 구현 불일치, 네이밍 정리.

**마지막 요약 표** — API 표면 × 점검 상태:

| 엔드포인트 | 버전관리 | 하위호환 | 스키마일관성 | 상태코드 | 엔티티노출 | 비고 |
|-----------|---------|---------|--------------|---------|-----------|------|
| GET /users | ❌ | ⚠️ | ✅ | ✅ | ❌ | User 엔티티 그대로 반환 |

그리고 심각도별 개수 한 줄: `Critical 1 · High 1 · Medium 0 · Low 0`.

---

## 규칙 (Do / Do-Not)

- **DO**: STEP 1에서 찾은 API 표면만 리뷰한다. 실제 `파일:라인`을 인용한다. 위치를 못 찾으면 "확인 불가"로 표시하고 지어내지 않는다.
- **DO**: 잘 설계된 부분도 요약 표에 ✅로 반영한다(문제만 나열하지 않음).
- **DO-NOT**: 이 프로젝트가 호출하는 외부 API의 신뢰성, 예외→상태코드 매핑 일관성, 입력 검증 존재 여부, 계층 의존성 위반 자체를 여기서 다루지 않는다(각각 `comm_review`·`error_review`·`validation_review`·`arch_review`로).
- **DO-NOT**: 근거 없는 추측성 지적을 하지 않는다.

## CLAUDE.md 연계

- API 계약은 presentation/controller 계층의 책임이다. 도메인 엔티티가 응답 DTO로 그대로 나가는 경우, 계약 안정성 리스크는 여기서 지적하되 계층 의존성 위반 자체의 심각도는 `arch_review`에서 함께 다룬다.
- 새 엔드포인트/스키마 필드 추가 직후 이 커맨드로 점검하면, 완료 정의를 만족하기 전에 하위 호환성 결함을 걸러낼 수 있다.
