# error_review — 예외 처리 전략 리뷰 렌즈

점검 대상: $ARGUMENTS

> 이 커맨드는 **코드베이스 전체의 예외 처리 방식**을 본다. 특정 통신·DB·동시성 문제의 원인 분석은 각 전문 커맨드의 몫이고, 여기서는 "그 실패가 결국 어떻게 잡히고, 어떤 응답/로그로 변환되고, 자원이 정리되는가"라는 **처리 계층**만 본다.
> "먼저 이 프로젝트의 예외 처리 구조(전역 핸들러, 커스텀 예외 계층 등)를 찾고(STEP 1) → 발견된 구조에만 해당 항목을 적용(STEP 2)"하는 순서를 반드시 지킨다.
> 사용법: `error_review [선택: 경로 또는 컴포넌트 이름]`
> - 인자 없음 → 프로젝트 전체 스캔
> - 인자 있음 → 해당 경로/컴포넌트로 범위 한정

---

## 범위 (Scope)

- **대상**: 예외/에러가 발생한 이후의 처리 — 표준 에러코드·HTTP/gRPC 상태 매핑, 전역 예외 핸들러, 커스텀 예외 계층, swallowed exception(삼킨 예외), 사용자 노출 메시지 vs 내부 로깅 분리, 실패 모드에서의 자원 정리(트랜잭션 롤백, 커넥션/파일 핸들 반납, 락 해제).
- **제외**: 특정 실패의 근본 원인 — DB 트랜잭션 설계(→ `db_review`), 다운스트림 호출 재시도/서킷 브레이커(→ `comm_review`), 락 경합·자원 누수의 동시성 원인(→ `concurrency_review`), 여러 리소스에 걸친 정합성(→ `consistency_review`), 레이어 경계(→ `arch_review`), API 계약·상태코드 설계 자체(→ `api_review`), 입력 검증이 애초에 존재하는지(→ `validation_review`, 여기서는 검증 실패 이후 그 예외가 처리되는 방식만 본다). 이 항목이 나오면 "범위 밖, 해당 커맨드로"라고만 표시하고, 대신 "그 예외가 처리되는 방식"만 본다.

---

## STEP 1 — 대상 인벤토리 (Discovery) · 반드시 먼저

코드베이스를 스캔해 **실제로 존재하는 예외 처리 구조만** 목록화한다. 없는 것은 리뷰하지 않는다.

탐지 신호:

| 종류 | 탐지 신호(예시) |
|------|----------------|
| 전역 예외 핸들러 | `@ExceptionHandler`/`@ControllerAdvice`, Express/Koa 에러 미들웨어, Go HTTP 미들웨어의 `recover()`, FastAPI `exception_handler`, gRPC interceptor |
| 커스텀 예외 계층 | 도메인별 Exception/Error 클래스, 에러 코드 enum·상수 |
| 에러 응답 포맷 | ErrorResponse DTO, JSON 에러 객체 스키마, gRPC status/details |
| 로깅 지점 | catch 블록 내 로깅 호출, 구조화 로깅(로그 필드에 요청 ID 등 포함 여부) |
| 자원 정리 구문 | try-with-resources/`using`/`defer`/`finally`로 커넥션·트랜잭션·파일 핸들을 닫는 패턴 |
| 패닉/크래시 복구 | `recover()`, 프로세스 레벨 uncaught exception 핸들러 |

**STEP 1 출력**: 발견된 예외 처리 구조를 먼저 요약한다.

| # | 컴포넌트 | 종류 | 적용 범위(전역/부분) | 파일:라인 |
|---|---------|------|----------------------|-----------|

- 하나도 못 찾으면(전역 핸들러도 커스텀 예외 계층도 없고 개별 catch만 산재): 리뷰를 생략하지 말고, catch 블록 자체를 STEP 2 A 항목 기준으로 개별 스캔한다(단, 나열이 너무 많으면 대표 패턴 위주로 샘플링하고 그 사실을 명시).
- 전역 핸들러가 있는지 불분명하면 진입점(main/router 설정)부터 확인한다.

## STEP 2 — 대상별 점검 (발견된 구조에만 적용)

### A. 공통 (모든 예외 처리 코드에 적용)
- **삼킨 예외(swallowed exception)**: catch 블록이 비어있거나 로그만 찍고 호출자에게 실패를 전파하지 않아, 실패가 성공처럼 보이는 경로가 있는가.
- **에러→상태 매핑 일관성**: 같은 종류의 실패(예: NotFound, ValidationError)가 엔드포인트마다 다른 HTTP 상태/에러 코드로 나가지 않는가.
- **사용자 노출 vs 내부 로깅 분리**: 스택트레이스, 내부 예외 메시지, SQL 구문, 파일 경로, 시크릿 등이 API 응답에 그대로 노출되는가. 내부 로그에는 충분한 컨텍스트(요청 ID, 입력값 요약)가 남는가.
- **실패 시 자원 정리**: 예외 발생 경로에서 트랜잭션 롤백, DB 커넥션 반납, 파일/락 해제가 예외 종류와 무관하게 항상 실행되는가(정상 경로에만 정리 코드가 있고 예외 경로엔 없는 경우가 흔한 결함).
- **예외 타입의 의미 구분**: 비즈니스 예외(재시도해도 소용없는 4xx성)와 시스템 예외(재시도 가능한 5xx성)가 구분되는가, 전부 generic `Exception`/`RuntimeException`으로 뭉뚱그려지지 않는가.

### B. 전역 예외 핸들러 (있을 때만)
- 모든 진입점(컨트롤러/핸들러)이 실제로 이 핸들러를 거치는가, 일부가 개별적으로 다르게 처리해 일관성이 깨지는가.
- 매핑되지 않은 예외(catch-all)에 대한 기본 폴백이 안전한 기본값(예: 500 + 일반화된 메시지)으로 떨어지는가, 내부 정보를 흘리지 않는가.

### C. 커스텀 예외 계층 (있을 때만)
- 예외 계층 구조가 의미 있게 분리되어 있는가(ValidationError/NotFoundError/ConflictError 등), 아니면 대부분 generic 예외로 처리되는가.
- 예외에 프로그래매틱하게 분기 가능한 에러 코드가 붙어 있는가.

### D. 비동기/동시성 경로의 예외 (비동기 코드가 있을 때만)
- 스레드/고루틴/Promise 경계를 넘는 예외가 로깅 없이 사라지는가(동시성 메커니즘 자체의 안전성은 `concurrency_review` 영역이지만, "그 안에서 던진 예외가 결국 어딘가에 기록되는가"는 여기서 본다).

### E. 자원 close 패턴 (파일/커넥션/락을 다루는 코드가 있을 때만)
- try-with-resources / `defer` / `using` 등으로 예외 발생 시에도 자원 해제가 보장되는가, 수동 close가 예외 경로에서 스킵될 수 있는 구조인가.

## STEP 3 — 출력 포맷 (일정하게)

각 발견은 아래 형식으로. 심각도 순(Critical→Low)으로 정렬한다.

```
[심각도] <한 줄 요약>
  대상 : <컴포넌트/경로>
  위치 : <파일:라인>
  근거 : <왜 문제인가 — STEP 2의 어떤 항목 위반인지>
  수정안: <구체적 조치 — 코드 수준>
```

**심각도 기준**
- `Critical`: 예외가 완전히 삼켜져 실패가 성공처럼 보임(silent failure), 실패 경로에서 트랜잭션 롤백/자원 정리 누락으로 데이터 오염 위험, 내부 스택트레이스·시크릿이 사용자 응답에 노출.
- `High`: 전역 핸들러 부재로 일부 엔드포인트가 raw 500/스택트레이스를 그대로 반환, 자원 누수(커넥션/파일 핸들 미반납).
- `Medium`: 에러 코드 체계 불일치, 로그에 추적 컨텍스트 부족.
- `Low`: 예외 계층 구조 개선 권장, 네이밍 정리.

**마지막 요약 표** — 컴포넌트 × 점검 상태:

| 컴포넌트 | 삼킨예외 | 매핑일관성 | 노출분리 | 자원정리 | 비고 |
|---------|---------|-----------|---------|---------|------|
| OrderController | ⚠️ | ❌ | ❌ | ✅ | 스택트레이스 그대로 응답 |

그리고 심각도별 개수 한 줄: `Critical 1 · High 1 · Medium 0 · Low 0`.

## 규칙 (Do / Do-Not)

- **DO**: STEP 1에서 찾은 구조/컴포넌트만 리뷰한다. 실제 `파일:라인`을 인용한다. 위치를 못 찾으면 "확인 불가"로 표시하고 지어내지 않는다.
- **DO**: 잘 처리된 경로도 요약 표에 ✅로 반영한다(문제만 나열하지 않음).
- **DO-NOT**: 실패의 근본 원인(왜 DB 쿼리가 실패했는지, 왜 다운스트림이 죽었는지)을 진단하지 않는다 — 그건 `db_review`/`comm_review`/`concurrency_review`/`consistency_review`의 몫이며, 여기서는 그 실패가 처리되는 방식만 본다.
- **DO-NOT**: 근거 없는 추측성 지적을 하지 않는다.

## CLAUDE.md 연계

- 전역 예외 핸들러는 대개 presentation/controller 계층에 위치한다. 도메인 계층에서 HTTP 상태 코드나 프레임워크 예외 타입을 직접 참조하면 그 자체가 계층 위반이며 `arch_review` 병행 검토 대상이다.
- 새 API 엔드포인트나 유스케이스 추가 직후 이 커맨드로 점검하면, 완료 정의를 만족하기 전에 예외 처리 누락을 걸러낼 수 있다.
