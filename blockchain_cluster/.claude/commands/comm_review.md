# comm_review — 외부 통신 리뷰 렌즈

점검 대상: $ARGUMENTS

> 이 커맨드는 **현재 프로젝트가 실제로 사용하는 외부 통신만** 대상으로 리뷰한다.
> 일반 체크리스트를 전부 나열하지 않는다. "먼저 무엇을 쓰는지 찾고(STEP 1) → 발견된 것에만 해당 항목을 적용(STEP 2)"하는 순서를 반드시 지킨다.
> 사용법: `comm_review [선택: 경로 또는 통합 이름]`
> - 인자 없음 → 프로젝트 전체 스캔
> - 인자 있음 → 해당 경로/통합으로 범위 한정

---

## 범위 (Scope)

- **대상**: 프로세스 밖과의 통신 — 외부 HTTP/REST 호출, gRPC, 메시지 브로커(Kafka/RabbitMQ/SQS 등), 서드파티 SDK(결제·스토리지 등), 웹훅.
- **제외**: DB 통신(→ `db_review`), 프로세스 내부 동시성(→ `concurrency_review`), 여러 리소스/서비스에 걸친 쓰기 정합성(→ `consistency_review`), 예외 처리·에러 매핑 방식(→ `error_review`), 우리가 제공하는 API의 계약·버전 관리(→ `api_review`), 입력 검증 존재 여부(→ `validation_review`), 인증/인가·시크릿 하드코딩·민감정보 로깅(→ `security_review`). 이 항목이 나오면 "범위 밖, 해당 커맨드로"라고만 표시하고 리뷰하지 않는다.

---

## STEP 1 — 대상 인벤토리 (Discovery) · 반드시 먼저

코드베이스를 스캔해 **실제로 존재하는 외부 통신만** 목록화한다. 없는 것은 리뷰하지 않는다.

탐지 신호(언어·프레임워크 무관하게 아래 패턴을 찾는다):

| 종류 | 탐지 신호(예시) |
|------|----------------|
| 외부 HTTP | HTTP 클라이언트 사용부(RestClient/WebClient/OkHttp/HttpClient/axios/fetch/requests/httpx/net/http), 외부 base URL 상수·설정 |
| gRPC | 생성된 stub, 채널 생성(ManagedChannel/grpc.Dial/insecure_channel), `*.proto` |
| 메시지 브로커 | producer/consumer, `@KafkaListener`/KafkaTemplate, amqp, SQS/SNS SDK, pub/sub |
| 서드파티 SDK | aws-sdk, 결제(stripe 등), 스토리지, 검색 등 외부 SaaS 클라이언트 |
| 웹훅 | 외부에서 들어오는 콜백 엔드포인트, 서명 검증 헤더 |
| 설정 | 환경변수·yaml의 외부 host/url/port/api key, 타임아웃·재시도 설정값 |

**STEP 1 출력**: 발견된 통합의 표를 먼저 제시한다.

| # | 통합 이름 | 종류 | 방향(out/in) | 진입 파일:라인 | 어댑터 위치 |
|---|-----------|------|--------------|----------------|-------------|

- 하나도 못 찾으면: 리뷰를 만들지 말고 "외부 통신을 찾지 못함. 통합이 있는데 못 찾았다면 경로를 알려달라"고 **한 번만** 묻는다.
- 애매한 것(내부/외부 불분명)만 모아서 함께 확인한다.

---

## STEP 2 — 대상별 점검 (발견된 종류에만 적용)

각 통합에 대해, **그 종류에 해당하는 항목만** 본다. 프로젝트에 없는 프로토콜의 항목은 절대 만들어내지 않는다(HTTP만 쓰면 gRPC 지적을 내지 않는다).

### A. 공통 (모든 외부 통신에 적용)
- **타임아웃**: connect/read/write 및 전체 deadline이 **명시적으로** 설정됐는가. 무한 대기 경로가 있는가.
- **재시도**: 지수 백오프 + jitter인가, 횟수 상한이 있는가, **한 계층에서만** 재시도하는가, 비멱등 요청을 무분별하게 재시도하지 않는가.
- **장애 격리 (resilience)**:
  - 서킷 브레이커가 있는가, 있다면 open/half-open/closed 전이 조건과 복구(half-open probe) 로직이 타당한가.
  - 폴백/graceful degradation: 다운스트림 장애 시 즉시 에러를 던지는 대신 대체 응답(캐시된 값, 기본값, 부분 성공)을 낼 수 있는 경로가 있는가.
  - **벌크헤드**: 다운스트림별로 스레드/커넥션 풀이 격리되어 있는가, 아니면 하나의 공용 풀을 여러 다운스트림이 나눠 써서 한 다운스트림의 장애가 나머지 호출까지 굶기는가.
  - **재시도 폭풍**: 여러 계층(클라이언트, 게이트웨이, 메시지 컨슈머 등)이 각자 재시도를 걸어 실제 요청량이 기하급수로 증폭되지 않는가. 다운스트림 장애 시 재시도가 오히려 장애를 심화시키지 않는가(thundering herd).
- **클라이언트 재사용**: 요청마다 새로 만들지 않고 싱글톤/풀로 재사용하는가.
- **관측성**: traceId/correlation ID를 헤더·메타데이터로 전파하는가. 홉별 지연·에러율·재시도가 계측되는가.
- **에러 처리**: 다운스트림 실패를 삼키지 않고 표준 에러로 매핑하는가. 실패 시 자원(커넥션·트랜잭션)을 정리하는가.
- **설정 외부화**: 엔드포인트/호스트가 하드코딩되지 않고 설정으로 외부화됐는가(시크릿 하드코딩·민감정보 로깅 자체는 `security_review` C/D 섹션 소관).
- **페이로드**: 필요한 필드만 주고받는가, 큰 응답에 압축을 쓰는가, 바이너리를 본문에 싣지 않는가.

### B. 외부 HTTP (HTTP 통합이 있을 때만)
- keep-alive/커넥션 풀 설정, 클라이언트 idle 타임아웃이 LB/서버보다 짧은가(커넥션 리셋 방지).
- HTTP/2 사용 가능 시 멀티플렉싱 활용 여부.
- 캐시 가능한 응답에 `Cache-Control`/`ETag` 및 조건부 요청 활용.
- 스트리밍/SSE 경로의 프록시 버퍼링 이슈.
- 429/5xx에 대한 처리(백오프, Retry-After 준수).

### C. gRPC (gRPC 통합이 있을 때만)
- deadline을 하류로 전파하고, 서버 핸들러가 context 취소/deadline을 확인해 조기 중단하는가.
- 채널 재사용 및 커넥션 편중(L4 뒤 고정) 대응 — 클라이언트 LB 또는 L7 프록시.
- 메시지 최대 크기 한도(기본 4MB) 초과 위험, 스트리밍 backpressure/흐름제어 준수.
- proto 스키마 진화의 런타임 파싱 안전성: 필드 번호 재사용 금지·삭제 시 `reserved`, 새 필드 optional, enum 미지값 처리(계약 관리 프로세스 자체는 `api_review` D 섹션 소관, 여기서는 "파싱이 깨지지 않는가"만).
- name resolution/LB 캐싱으로 스케일아웃 인스턴스 누락 여부.

### D. 메시지 브로커 (Kafka/RabbitMQ/SQS 등이 있을 때만)
- **소비자 멱등성/중복 제거**(at-least-once 전제), 순서 보장 필요 시 파티션 키.
- ack/commit 시점이 처리 완료 후인가(조기 커밋으로 유실 위험 없는가).
- DLQ/독약 메시지 처리, 무한 재처리 루프 방지.
- 컨슈머 lag/backpressure 대응, 배치 크기·폴링 설정.

### E. 서드파티 SDK / 외부 SaaS (있을 때만)
- **멱등성 키**(특히 결제·주문 등 비멱등 작업).
- SDK 기본 타임아웃 확인(다수 SDK가 무한/과대 기본값) 및 재정의.
- rate limit(429) 백오프, 쿼터 초과 처리.
- SDK 클라이언트 재사용, 시크릿·자격증명 관리.

### F. 웹훅(수신) (있을 때만)
- 서명/HMAC 검증으로 위조 요청 차단.
- 멱등 처리(중복 콜백), 재시도되는 발신자 특성 고려.
- 빠른 200 응답 후 비동기 처리(발신 측 타임아웃 방지).

## STEP 3 — 출력 포맷 (일정하게)

각 발견은 아래 형식으로. 심각도 순(Critical→Low)으로 정렬한다.

```
[심각도] <한 줄 요약>
  대상 : <통합 이름 / 프로토콜>
  위치 : <파일:라인>
  근거 : <왜 문제인가 — STEP 2의 어떤 항목 위반인지>
  수정안: <구체적 조치 — 코드/설정 수준>
```

**심각도 기준**
- `Critical`: 장애 전파·데이터 유실·중복 결제 등 즉시 사고로 이어짐(타임아웃 없음, 비멱등 재시도, ack 조기 커밋, 서킷 브레이커 없이 연쇄 장애 전파 등).
- `High`: 부하 시 병목·간헐 장애(커넥션 미재사용, 재시도 폭풍/무한 증폭, backpressure 무시, 벌크헤드 미적용으로 다운스트림 간 자원 경합).
- `Medium`: 성능·운영성 저하(압축 없음, 캐시 미활용, traceId 누락).
- `Low`: 개선 권장(설정 정리, 스키마 진화 관례).

**마지막 요약 표** — 통합 × 점검 상태:

| 통합 | 타임아웃 | 재시도 | 장애격리 | 재사용 | 관측 | 종류별 | 비고 |
|------|---------|--------|---------|--------|------|--------|------|
| PaymentAPI | ⚠️ | ❌ | ❌ | ✅ | ⚠️ | 멱등키 없음 | Critical 1 |

그리고 심각도별 개수 한 줄: `Critical 1 · High 3 · Medium 2 · Low 1`.

## 규칙 (Do / Do-Not)

- **DO**: STEP 1에서 찾은 통합만 리뷰한다. 실제 `파일:라인`을 인용한다. 위치를 못 찾으면 "확인 불가"로 표시하고 지어내지 않는다.
- **DO**: 항목이 잘 지켜진 경우도 요약 표에 ✅로 반영한다(문제만 나열하지 않음).
- **DO-NOT**: 프로젝트에 없는 프로토콜/패턴의 지적을 만들지 않는다.
- **DO-NOT**: DB·내부 동시성·다중 리소스 정합성·예외 처리 방식 문제를 여기서 다루지 않는다(각각 `db_review`·`concurrency_review`·`consistency_review`·`error_review`로).
- **DO-NOT**: 설계 문서/코드에 근거 없는 추측성 지적을 하지 않는다.

## CLAUDE.md 연계

- 이 리뷰가 지적하는 통신 로직은 대개 `infrastructure/adapter`(외부 어댑터)와 `presentation/controller`에 위치한다. 도메인 계층에서 외부 통신 흔적이 발견되면 그 자체가 `Critical`(계층 의존성 위반, `arch_review` 병행 권고).
- 코드 생성(§5 STEP 4·5) 직후 이 커맨드로 점검하면, 완료 정의(§10)를 만족하기 전에 통신 결함을 걸러낼 수 있다.
