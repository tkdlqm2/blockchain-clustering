# concurrency_review — 동시성 리뷰 렌즈

점검 대상: $ARGUMENTS

> 이 커맨드는 **현재 프로젝트가 실제로 쓰는 동시성 메커니즘만** 대상으로 리뷰한다.
> 일반 체크리스트를 전부 나열하지 않는다. "먼저 무엇을 쓰는지 찾고(STEP 1) → 발견된 것에만 해당 항목을 적용(STEP 2)"하는 순서를 반드시 지킨다.
> 사용법: `concurrency_review [선택: 경로 또는 컴포넌트 이름]`
> - 인자 없음 → 프로젝트 전체 스캔
> - 인자 있음 → 해당 경로/컴포넌트로 범위 한정

---

## 범위 (Scope)

- **대상**: 단일 프로세스 안에서의 동시 실행 — 스레드/고루틴, 락/뮤텍스, 스레드·워커 풀, 비동기(Future/Promise/coroutine), 채널/큐(인메모리), 공유 가변 상태(캐시, 싱글톤, static 필드), 스케줄러/백그라운드 작업.
- **제외**: DB 트랜잭션/행 락(→ `db_review`), 외부 네트워크 통신의 재시도·타임아웃(→ `comm_review`), 레이어/모듈 경계(→ `arch_review`), 여러 리소스에 걸친 정합성(→ `consistency_review`), 예외가 잡힌 이후의 처리 방식(→ `error_review`, 여기서는 "예외가 스레드 경계를 넘어 사라지는가"만 보고 그 이후 매핑/로깅은 다루지 않는다). 이 항목이 나오면 "범위 밖, 해당 커맨드로"라고만 표시하고 리뷰하지 않는다.

---

## STEP 1 — 대상 인벤토리 (Discovery) · 반드시 먼저

코드베이스를 스캔해 **실제로 존재하는 동시성 메커니즘만** 목록화한다. 없는 것은 리뷰하지 않는다.

탐지 신호(언어·프레임워크 무관하게 아래 패턴을 찾는다):

| 종류 | 탐지 신호(예시) |
|------|----------------|
| 스레드/고루틴 생성 | `go func`, `Thread`/`Runnable`, `threading.Thread`, `worker_threads`, `std::thread` |
| 락/동기화 | `sync.Mutex`/`RWMutex`, `synchronized`, `ReentrantLock`, `threading.Lock`, `Arc<Mutex<>>` |
| 원자 연산 | `sync/atomic`, `AtomicInteger`, `atomic` 모듈 |
| 스레드/워커 풀 | `ExecutorService`, `goroutine pool`, `ThreadPoolExecutor`, `worker_threads` pool, 커스텀 워커 큐 |
| 비동기/Future | `async/await`, `CompletableFuture`, `Promise`, Kotlin `coroutine`/`launch`/`async` |
| 채널/큐(인메모리) | Go `channel`, `queue.Queue`, `BlockingQueue`, actor mailbox |
| 공유 가변 상태 | 전역/static 변수, 싱글톤 필드, 요청 간 재사용되는 인메모리 캐시(`map`, `HashMap`, 등)에 대한 쓰기 |
| 스케줄러/백그라운드 | cron, `Ticker`, `@Scheduled`, `setInterval`, 백그라운드 워커 루프 |
| 동시성 유틸 설정 | 풀 크기, 큐 용량, `sync.Once`, double-checked locking 초기화 |

**STEP 1 출력**: 발견된 동시성 구성요소의 표를 먼저 제시한다.

| # | 컴포넌트/위치 | 종류 | 공유 상태 존재 여부 | 언어/프레임워크 방식 | 파일:라인 |
|---|--------------|------|---------------------|----------------------|-----------|

- 하나도 못 찾으면: 리뷰를 만들지 말고 "동시성 코드를 찾지 못함. 있는데 못 찾았다면 경로를 알려달라"고 **한 번만** 묻는다.
- 애매한 것(동시성 코드인지 단순 비동기 I/O 래핑인지 불분명)만 모아서 함께 확인한다.

## STEP 2 — 대상별 점검 (발견된 종류에만 적용)

각 컴포넌트에 대해, **그 종류에 해당하는 항목만** 본다. 프로젝트에 없는 메커니즘의 항목은 절대 만들어내지 않는다(고루틴만 쓰면 Java `synchronized` 지적을 내지 않는다).

### A. 공통 (모든 동시성 코드에 적용)
- **데이터 경쟁**: 둘 이상의 스레드/고루틴이 락 없이 같은 가변 상태를 읽고 쓰는가.
- **락 범위**: 락이 필요한 최소 구간만 감싸는가. 락을 쥔 채로 외부 호출·DB 접근·긴 계산을 하지 않는가(다운스트림 문제는 각각 comm_review/db_review로 넘기되, "락을 오래 쥐는" 동시성 관점은 여기서 지적).
- **락 순서 일관성**: 여러 락을 동시에 잡는 경로가 있다면 모든 경로가 동일한 순서로 잡는가(교착 방지).
- **자원 누수**: 고루틴/스레드가 종료 조건 없이 무한 대기하거나(고루틴 릭), context 취소·인터럽트 시 정리되는가.
- **공유 캐시/싱글톤 스레드 안전성**: 스레드 세이프하지 않은 자료구조(plain map/HashMap 등)를 동시 접근 경로에서 그대로 쓰는가.
- **초기화 경쟁**: 지연 초기화(lazy singleton)가 `sync.Once`/`volatile` + double-checked locking 등으로 안전하게 보호되는가.

### B. 스레드/워커 풀 (풀이 있을 때만)
- 풀 크기 산정 근거가 있는가(무작정 크게 잡아 컨텍스트 스위칭·메모리 낭비 유발하지 않는가).
- 큐가 무제한으로 쌓이지 않는가(백프레셔 없는 unbounded queue).
- 태스크 내 예외가 풀 전체를 죽이지 않는가(uncaught exception 처리).
- 그레이스풀 셧다운(진행 중 작업 대기 후 종료) 처리 여부.

### C. 비동기/Future/Promise (있을 때만)
- 에러가 삼켜지지 않는가(unhandled rejection, `CompletableFuture`의 예외가 로깅 없이 사라지는 경우).
- 여러 비동기 작업을 모을 때(`Promise.all`, `WaitGroup`, `errgroup`) 부분 실패 처리가 명확한가.
- 콜백/체인 합성이 과도하게 복잡해 실패 지점 추적이 어렵지 않은가.

### D. 채널/큐(인메모리) (있을 때만)
- 채널 버퍼 크기와 블로킹 여부, 송신자만 있고 수신자가 없어 고루틴이 영원히 블록되는 경로가 있는가.
- `select`/타임아웃 처리로 무한 대기를 방지하는가.

### E. 스케줄러/백그라운드 작업 (있을 때만)
- 이전 실행이 끝나지 않았는데 다음 트리거가 겹쳐 중복 실행되는 걸 막는가.
- 실패 시 알림·재시도 정책이 있는가, 무한 재시도 루프가 아닌가.

### F. 언어별 특이사항 (감지된 언어에만 적용)
- **Go**: `go test -race` 대상인가, context가 고루틴 트리로 제대로 전파되는가.
- **Java/Kotlin**: `synchronized`와 `java.util.concurrent`가 혼용되어 락 대상이 불명확하지 않은가, coroutine scope가 상위 작업 취소 시 함께 취소되는가.
- **Python**: GIL 특성상 CPU-bound 작업에 `threading`을 쓰는 게 실효가 없지 않은가(멀티프로세싱 필요 여부), `asyncio` 이벤트 루프 안에서 블로킹 동기 코드를 호출하지 않는가.
- **JS/Node**: 이벤트 루프를 블로킹하는 무거운 동기 연산이 있는가, 필요 시 `worker_threads` 분리를 검토했는가.

## STEP 3 — 출력 포맷 (일정하게)

각 발견은 아래 형식으로. 심각도 순(Critical→Low)으로 정렬한다.

```
[심각도] <한 줄 요약>
  대상 : <컴포넌트 이름>
  위치 : <파일:라인>
  근거 : <왜 문제인가 — STEP 2의 어떤 항목 위반인지>
  수정안: <구체적 조치 — 코드 수준>
```

**심각도 기준**
- `Critical`: 데이터 경쟁, 교착(deadlock), 자원 고갈로 이어지는 스레드/고루틴 누수.
- `High`: 락을 쥔 채 I/O 수행, unbounded 풀/큐, 예외로 인한 풀 전체 마비.
- `Medium`: 그레이스풀 셧다운 누락, 비동기 에러 스와핑, 중복 스케줄 실행 위험.
- `Low`: 설정 튜닝 권장, 네이밍/구조 개선.

**마지막 요약 표** — 컴포넌트 × 점검 상태:

| 컴포넌트 | 데이터경쟁 | 락범위 | 자원누수 | 풀/큐설정 | 에러처리 | 비고 |
|---------|-----------|--------|---------|-----------|---------|------|
| CacheManager | ⚠️ | ❌ | ✅ | - | ✅ | 락 없이 map 쓰기 |

그리고 심각도별 개수 한 줄: `Critical 1 · High 2 · Medium 1 · Low 0`.

## 규칙 (Do / Do-Not)

- **DO**: STEP 1에서 찾은 컴포넌트만 리뷰한다. 실제 `파일:라인`을 인용한다. 위치를 못 찾으면 "확인 불가"로 표시하고 지어내지 않는다.
- **DO**: 항목이 잘 지켜진 경우도 요약 표에 ✅로 반영한다(문제만 나열하지 않음).
- **DO-NOT**: 프로젝트에 없는 동시성 메커니즘의 지적을 만들지 않는다.
- **DO-NOT**: DB 락·외부 통신 재시도·레이어 경계 문제를 여기서 다루지 않는다(각각 `db_review`·`comm_review`·`arch_review`로).
- **DO-NOT**: 근거 없는 추측성 지적을 하지 않는다.

## CLAUDE.md 연계

- 동시성 제어 코드(락, 세션 직렬화 등)는 대개 인프라/클라이언트 어댑터 계층에 위치한다. 도메인 계층에서 스레드/락을 직접 다루는 코드가 발견되면 그 자체가 `Critical`이며 `arch_review` 병행 검토 대상이다.
- 코드 생성 직후 `db_review`/`comm_review`와 함께 이 커맨드로 점검하면, 완료 정의를 만족하기 전에 동시성 결함을 걸러낼 수 있다.
