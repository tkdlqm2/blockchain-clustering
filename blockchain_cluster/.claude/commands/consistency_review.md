# consistency_review — 데이터 정합성 리뷰 렌즈

점검 대상: $ARGUMENTS

> 이 커맨드는 **하나의 비즈니스 오퍼레이션이 둘 이상의 리소스(DB+DB, DB+브로커, 서비스A+서비스B)에 걸쳐 쓰기를 할 때 최종적으로 정합적인가**만 본다.
> 단일 DB 트랜잭션 하나의 정확성은 `db_review`, 단일 통신 호출/컨슈머 하나의 신뢰성은 `comm_review`가 이미 다룬다 — 여기서는 **그 여러 쓰기를 하나로 묶는 경계 자체**를 본다.
> "먼저 어떤 다중 리소스 쓰기 경로가 있는지 찾고(STEP 1) → 발견된 경로에만 해당 항목을 적용(STEP 2)"하는 순서를 반드시 지킨다.
> 사용법: `consistency_review [선택: 경로 또는 유스케이스 이름]`
> - 인자 없음 → 프로젝트 전체 스캔
> - 인자 있음 → 해당 경로/유스케이스로 범위 한정

---

## 범위 (Scope)

- **대상**: 하나의 논리적 오퍼레이션이 둘 이상의 리소스(여러 DB/테이블 경계를 넘는 쓰기 + 메시지 발행, 여러 서비스 호출)에 걸쳐 일어날 때의 정합성 — 트랜잭셔널 아웃박스, saga/보상 트랜잭션, 분산 멱등성 키, 최종 일관성(eventual consistency) 처리, 이벤트 순서 보장과 중복 소비 방지.
- **제외**: 단일 DB 트랜잭션/쿼리 자체의 정확성(→ `db_review`), 단일 외부 호출·단일 컨슈머의 재시도/타임아웃(→ `comm_review`), 락/스레드 동시성(→ `concurrency_review`), 레이어 경계(→ `arch_review`). 이 항목이 나오면 "범위 밖, 해당 커맨드로"라고만 표시하고 리뷰하지 않는다.

---

## STEP 1 — 대상 인벤토리 (Discovery) · 반드시 먼저

코드베이스를 스캔해 **실제로 여러 리소스에 걸쳐 쓰기가 일어나는 경로만** 목록화한다. 없는 것은 리뷰하지 않는다.

탐지 신호:

| 종류 | 탐지 신호(예시) |
|------|----------------|
| DB 쓰기 + 메시지 발행 동시 수행 | 같은 함수/트랜잭션 안에서 DB commit과 producer.send/publish가 함께 있는 경우 (dual write 의심) |
| 아웃박스 패턴 | `outbox` 테이블, 별도 릴레이/폴러 프로세스가 outbox를 읽어 브로커로 발행 |
| Saga / 보상 트랜잭션 | 여러 단계를 순차 호출하고 실패 시 역순으로 되돌리는 로직(`compensate`, `rollback step`, saga orchestrator/코레오그래피) |
| 여러 서비스에 걸친 쓰기 | 한 유스케이스 안에서 서로 다른 서비스(HTTP/gRPC 호출)에 순차적으로 상태 변경을 요청하는 경우 |
| 멱등성 키 저장소 | 요청 ID/멱등키를 별도 테이블·캐시에 저장해 중복 처리를 막는 코드 |
| 이벤트 순서/중복 소비 처리 | 이벤트에 버전/시퀀스 번호가 있는지, 컨슈머가 순서를 검증하거나 중복 이벤트를 걸러내는 로직 |

**STEP 1 출력**: 발견된 다중 리소스 쓰기 경로의 표를 먼저 제시한다.

| # | 유스케이스/경로 | 관련 리소스(2개 이상) | 패턴(dual-write/outbox/saga/없음) | 파일:라인 |
|---|-----------------|------------------------|-----------------------------------|-----------|

- 하나도 못 찾으면: 리뷰를 만들지 말고 "여러 리소스에 걸친 쓰기 경로를 찾지 못함. 있는데 못 찾았다면 유스케이스를 알려달라"고 **한 번만** 묻는다.
- 단일 리소스 쓰기인지 다중 리소스 쓰기인지 애매한 경우만 모아서 함께 확인한다.

## STEP 2 — 대상별 점검 (발견된 패턴에만 적용)

각 경로에 대해, **그 패턴에 해당하는 항목만** 본다. 존재하지 않는 패턴(예: saga가 없는데 보상 트랜잭션 부재를 지적)을 만들어내지 않는다.

### A. 공통 (다중 리소스 쓰기가 하나라도 있을 때)
- **Dual-write 문제**: DB 쓰기와 메시지 발행(또는 다른 서비스 호출)이 하나의 원자적 단위로 보장되지 않고 각각 따로 커밋되는가 — 중간에 프로세스가 죽으면 한쪽만 반영될 수 있는가.
- **부분 실패 처리**: 여러 단계 중 일부만 성공했을 때 시스템이 불일치 상태로 남는가, 아니면 감지·복구(재처리/보상)할 방법이 있는가.
- **멱등성**: 같은 오퍼레이션이 재시도/중복 실행되어도 최종 상태가 같은가(멱등키 존재 여부, 멱등키의 스코프가 실제 비즈니스 단위와 일치하는가).
- **가시성**: 불일치가 발생했을 때 탐지할 수 있는 수단(정합성 체크 배치, 알림, 재처리 큐)이 있는가, 아니면 조용히 유실되는가.

### B. 트랜잭셔널 아웃박스 (아웃박스 테이블이 있을 때만)
- 아웃박스 insert가 원본 DB 쓰기와 **같은 트랜잭션** 안에서 일어나는가.
- 릴레이/폴러가 발행 성공 후에만 아웃박스 레코드를 완료 처리하는가(최소 1회 발행 보장), 발행 실패 시 재시도 전략이 있는가.
- 아웃박스 테이블이 무한정 쌓이지 않도록 정리(archive/delete) 정책이 있는가.

### C. Saga / 보상 트랜잭션 (있을 때만)
- 각 단계에 대응하는 보상 로직이 실제로 존재하는가(일부 단계만 보상 가능하고 나머지는 누락되지 않았는가).
- 보상 자체가 실패할 경우의 처리(재시도, 수동 개입 큐, 알림)가 있는가.
- saga 상태(진행 중/완료/보상 중)가 영속화되어 프로세스 재시작 후에도 이어서 처리 가능한가.

### D. 여러 서비스에 걸친 순차 쓰기 (saga 없이 그냥 순차 호출만 있는 경우)
- 중간 호출이 실패했을 때 이미 반영된 앞 단계 상태를 되돌리거나 보정하는 로직이 전혀 없는 채로 방치되는가(암묵적 saga 필요 상황을 놓친 경우) — 이 경우 saga/보상 도입 필요성을 `High`로 지적.

### E. 이벤트 순서 / 중복 소비 (이벤트 기반 처리가 있을 때만)
- 이벤트에 순서 보장이 필요한 경우 파티션 키/시퀀스 번호로 순서를 지키는가, 컨슈머가 out-of-order 이벤트를 감지하는가.
- 동일 이벤트가 최소 1회 이상 전달될 수 있음을 전제로 컨슈머가 멱등하게 처리하는가(멱등키, upsert, 버전 체크).
- 이벤트 스키마 진화 시 과거 이벤트를 여전히 올바르게 소비할 수 있는가.

## STEP 3 — 출력 포맷 (일정하게)

각 발견은 아래 형식으로. 심각도 순(Critical→Low)으로 정렬한다.

```
[심각도] <한 줄 요약>
  대상 : <유스케이스/경로 이름>
  위치 : <파일:라인>
  근거 : <왜 정합성이 깨지는가 — STEP 2의 어떤 항목 위반인지>
  수정안: <구체적 조치 — 아웃박스 도입/보상 로직 추가/멱등키 적용 등>
```

**심각도 기준**
- `Critical`: dual-write로 인한 데이터 유실/불일치가 사용자에게 직접 영향(결제는 됐는데 주문은 안 만들어짐 등), 보상 로직 부재로 부분 실패 시 영구 불일치.
- `High`: 멱등성 부재로 재시도 시 중복 처리 위험, 아웃박스/saga 상태가 프로세스 재시작 시 유실.
- `Medium`: 불일치 탐지 수단 부재(모니터링/재처리 없음), 이벤트 순서 처리 미흡.
- `Low`: 아웃박스 정리 정책 부재 등 운영성 개선.

**마지막 요약 표** — 경로 × 점검 상태:

| 유스케이스 | dual-write | 멱등성 | 보상/복구 | 가시성 | 비고 |
|-----------|-----------|--------|-----------|--------|------|
| 주문생성+결제이벤트발행 | ❌ | ⚠️ | ❌ | ❌ | outbox 없음 |

그리고 심각도별 개수 한 줄: `Critical 1 · High 1 · Medium 0 · Low 0`.

---

## 규칙 (Do / Do-Not)

- **DO**: STEP 1에서 찾은 다중 리소스 쓰기 경로만 리뷰한다. 실제 `파일:라인`을 인용한다. 위치를 못 찾으면 "확인 불가"로 표시하고 지어내지 않는다.
- **DO**: 잘 처리된 경로도 요약 표에 ✅로 반영한다(문제만 나열하지 않음).
- **DO-NOT**: 단일 리소스 쓰기(리소스 하나짜리 트랜잭션)를 이 커맨드로 지적하지 않는다 — `db_review` 영역.
- **DO-NOT**: 단일 호출/컨슈머의 타임아웃·재시도 세부는 다루지 않는다 — `comm_review` 영역.
- **DO-NOT**: 근거 없는 추측성 지적을 하지 않는다.

## CLAUDE.md 연계

- 정합성이 필요한 유스케이스는 대개 애플리케이션 서비스/유스케이스 계층에 오케스트레이션 로직으로 존재한다. 이 로직이 도메인 계층에 섞여 있으면 `arch_review` 병행 검토 대상.
- 새 유스케이스가 둘 이상의 리소스에 쓰기를 하도록 설계된 직후 이 커맨드로 점검하면, 완료 정의를 만족하기 전에 dual-write/멱등성 결함을 걸러낼 수 있다.
