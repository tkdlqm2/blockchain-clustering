# validation_review — 입력 검증 리뷰 렌즈

점검 대상: $ARGUMENTS

> 이 커맨드는 **신뢰 경계를 넘는 입력에 대한 방어가 실제로 존재하는가**만 본다.
> 검증이 실패했을 때 그 실패가 어떤 응답/로그로 변환되는지는 `error_review`, API 계약 자체의 스키마 설계는 `api_review`가 본다 — 여기서는 "애초에 검증이 있는가, 이중 방어인가, 우회 가능한가"만 본다.
> "먼저 이 프로젝트의 신뢰 경계 진입점을 찾고(STEP 1) → 발견된 진입점에만 해당 항목을 적용(STEP 2)"하는 순서를 반드시 지킨다.
> 사용법: `validation_review [선택: 경로 또는 진입점 이름]`
> - 인자 없음 → 프로젝트 전체 스캔
> - 인자 있음 → 해당 경로/진입점으로 범위 한정

---

## 범위 (Scope)

- **대상**: 신뢰 경계를 넘는 모든 입력 — HTTP 요청(바디/쿼리/헤더/경로 파라미터), 메시지 브로커 컨슈머 페이로드, 파일 업로드, CLI 인자, 설정/환경변수. 경계(형식) 검증과 도메인(비즈니스 규칙) 검증의 이중 방어 여부, 입력 크기·개수 상한, 정규화, injection(SQL/커맨드/경로) 방지.
- **제외**: 검증 실패 시 에러 응답/상태코드 매핑(→ `error_review`), API 응답 스키마·버전 관리(→ `api_review`), 여러 리소스에 걸친 정합성(→ `consistency_review`), DB 쿼리 자체의 성능(→ `db_review`), 인증/인가·IDOR·시크릿 관리(→ `security_review`, 이 리뷰는 "값이 유효한 형식/규칙을 따르는가"만 보고 "이 사용자가 이 값에 접근할 권한이 있는가"는 다루지 않는다). 이 항목이 나오면 "범위 밖, 해당 커맨드로"라고만 표시하고 리뷰하지 않는다.

---

## STEP 1 — 대상 인벤토리 (Discovery) · 반드시 먼저

코드베이스를 스캔해 **실제로 존재하는 신뢰 경계 진입점만** 목록화한다. 없는 것은 리뷰하지 않는다.

탐지 신호:

| 종류 | 탐지 신호(예시) |
|------|----------------|
| HTTP 요청 | 컨트롤러 파라미터, 요청 바디 바인딩(`@RequestBody`, `req.body`, Pydantic 모델 등) |
| 검증 프레임워크 | `@Valid`/`@NotNull`, `class-validator`, `Joi`/`Zod`/`Yup`, `pydantic`, Go `validator` 태그, 수동 if-검증 코드 |
| 메시지 컨슈머 페이로드 | producer/consumer 핸들러의 역직렬화 직후 코드 |
| 파일 업로드 | multipart 핸들러, 업로드 크기·확장자 체크 코드 |
| CLI/배치 인자 | `flag`/`argparse`/`cobra` 등 인자 파싱부 |
| 설정/환경변수 | 설정 로드 시점의 필수값 검증 |
| 정규화 코드 | trim/lowercase/유니코드 정규화 함수 호출 |
| Injection 방지 흔적 | 파라미터 바인딩(prepared statement) vs 문자열 결합 SQL, 커맨드 실행 시 사용자 입력 포함 여부 |

**STEP 1 출력**: 발견된 신뢰 경계 진입점의 표를 먼저 제시한다.

| # | 진입점 | 종류(HTTP/브로커/파일/CLI/설정) | 검증 프레임워크 사용 여부 | 파일:라인 |
|---|--------|----------------------------------|----------------------------|-----------|

- 하나도 못 찾으면: 리뷰를 만들지 말고 "신뢰 경계 진입점을 찾지 못함. 있는데 못 찾았다면 경로를 알려달라"고 **한 번만** 묻는다.
- 내부 호출인지 외부 신뢰 경계인지 애매한 경우만 모아서 함께 확인한다.

## STEP 2 — 대상별 점검 (발견된 종류에만 적용)

### A. 공통 (모든 신뢰 경계 진입점에 적용)
- **경계(형식) 검증**: 타입·필수 여부·형식(이메일, 날짜, 열거값 등)이 진입점에서 검증되는가, 아니면 검증 없이 바로 도메인 로직으로 흘러가는가.
- **도메인(비즈니스 규칙) 검증 — 이중 방어**: 경계 검증을 통과한 값이라도 비즈니스 불변식(예: 잔액 ≥ 0, 상태 전이 유효성, 권한 범위)이 도메인 계층에서 별도로 재검증되는가, 아니면 컨트롤러의 형식 검증만 믿고 도메인 로직이 무방비인가.
- **크기·개수 상한**: 배열/리스트 파라미터, 파일 업로드, 페이지네이션 limit 등에 상한이 있는가(무제한 크기로 인한 메모리 고갈·DoS 위험).
- **정규화**: 검증 이전에 대소문자·공백·유니코드 정규화가 일어나 필터 우회를 막는가(예: 이메일 대소문자, 전각/반각 문자로 중복 체크 우회).
- **Injection 방지**: SQL/커맨드/경로 조작에 사용자 입력이 문자열 결합으로 그대로 들어가지 않는가(파라미터 바인딩·이스케이프·allowlist 사용 여부).
- **신뢰 경계 우회 여부**: 내부 서비스 간 호출이라는 이유로 검증을 생략하지 않는가 — 신뢰 경계를 넘는 입력은 호출 주체와 무관하게 재검증 대상인가.

### B. 메시지 컨슈머 페이로드 (브로커 컨슈머가 있을 때만)
- 컨슈머가 역직렬화 직후 페이로드 스키마를 검증하는가, 아니면 바로 도메인 로직에 넘기는가(변조되거나 스키마가 어긋난 메시지가 그대로 처리될 위험).

### C. 파일 업로드 (있을 때만)
- 파일 크기·확장자 검증과 함께 실제 콘텐츠 타입을 확인하는가(확장자만 믿지 않는지), 경로 조작(path traversal) 방지가 있는가.

### D. 설정/환경변수 (있을 때만)
- 필수 설정값이 없을 때 안전하게 기동을 실패시키는가, 아니면 조용히 기본값으로 넘어가 예상 밖 동작을 하는가.

## STEP 3 — 출력 포맷 (일정하게)

각 발견은 아래 형식으로. 심각도 순(Critical→Low)으로 정렬한다.

```
[심각도] <한 줄 요약>
  대상 : <진입점 이름>
  위치 : <파일:라인>
  근거 : <왜 문제인가 — STEP 2의 어떤 항목 위반인지>
  수정안: <구체적 조치 — 검증 규칙 추가/이중 방어 도입/상한 설정 등>
```

**심각도 기준**
- `Critical`: injection이 가능한 경로(문자열 결합 SQL/커맨드), 경계 검증도 도메인 검증도 없어 임의 입력이 그대로 실행·저장됨.
- `High`: 크기·개수 상한 없어 DoS 가능, 이중 방어 중 한쪽만 존재(형식 검증만 있고 도메인 규칙 검증이 없음 등).
- `Medium`: 정규화 누락으로 인한 우회 가능성, 내부 호출 경로에서 검증 생략.
- `Low`: 검증 메시지 품질, 설정 검증 개선 권장.

**마지막 요약 표** — 진입점 × 점검 상태:

| 진입점 | 경계검증 | 도메인검증 | 크기상한 | 정규화 | Injection방지 | 비고 |
|--------|---------|-----------|---------|--------|----------------|------|
| POST /transfer | ✅ | ❌ | ⚠️ | - | ✅ | 잔액 재검증 없음 |

그리고 심각도별 개수 한 줄: `Critical 1 · High 1 · Medium 0 · Low 0`.

---

## 규칙 (Do / Do-Not)

- **DO**: STEP 1에서 찾은 진입점만 리뷰한다. 실제 `파일:라인`을 인용한다. 위치를 못 찾으면 "확인 불가"로 표시하고 지어내지 않는다.
- **DO**: 잘 방어된 진입점도 요약 표에 ✅로 반영한다(문제만 나열하지 않음).
- **DO-NOT**: 검증 실패 이후의 에러 응답/상태코드, API 스키마·버전 설계, 여러 리소스 정합성 문제를 여기서 다루지 않는다(각각 `error_review`·`api_review`·`consistency_review`로).
- **DO-NOT**: 근거 없는 추측성 지적을 하지 않는다.

## CLAUDE.md 연계

- 경계 검증은 대개 presentation/controller 계층, 도메인 검증은 domain 계층에 위치한다. 도메인 계층에 검증이 전혀 없고 컨트롤러의 형식 검증만 존재한다면, 다른 진입 경로(배치, 내부 API, 메시지 컨슈머)로 우회 시 무방비가 되는 구조적 위험이며 `arch_review` 병행 검토 대상이다.
- 새 입력 진입점 추가 직후 이 커맨드로 점검하면, 완료 정의를 만족하기 전에 검증 누락을 걸러낼 수 있다.
