# 멀티체인 인덱서 — 설계 스펙 패키지

> **이 패키지의 목적**: 인덱서(블록체인 노드 → BalanceDelta → Kafka)를 처음부터 완성도 높게 개발할 수 있도록, 요구사항·데이터 모델·추출 알고리즘·아키텍처·구현 계획·계약 결정을 명세한다.
>
> **인덱서는 클러스터링 시스템과 별개의 프로젝트다.** 클러스터링 시스템은 이미 완성되어 있고, 그 시스템이 소비자로서 요구하는 데이터 계약이 **연동 계약 문서(클러스터링 팀의 문서 08, 이하 "계약")** 로 확정되어 있다. 이 인덱서 패키지는 그 계약을 **출력 경계의 고정점**으로 삼는다. 즉 인덱서가 무엇을 어떤 형식으로 내보내야 하는지는 이미 정해져 있고(§고정), 그것을 어떻게 만들어낼지가 이 패키지의 설계 대상이다.

## 문서 구성 (읽는 순서)

| 문서 | 내용 | 핵심 질문 |
|---|---|---|
| **00-README** (이 문서) | 개요·경계·고정 계약·용어집 | 무엇을·어떻게 읽는가 |
| **01-functional-spec** | 기능 요구사항·범위·비범위 | 인덱서가 무엇을 하는가 |
| **02-data-model-and-output-contract** | 내부 상태 모델 + 고정 출력 계약(Kafka 메시지) | 무엇을 저장·출력하는가 |
| **03-extraction-and-reorg-algorithms** | 체인별 BalanceDelta 추출 + reorg 감지 | 어떻게 만들어내는가 (핵심) |
| **04-architecture-and-interfaces** | 컴포넌트 분해·인터페이스·어댑터 패턴 | 어떻게 조립하는가 |
| **05-implementation-plan-and-tests** | 마일스톤·인수 기준·테스트 매트릭스 | 어떤 순서로·어떻게 검증하는가 |
| **06-contract-decisions** | 계약 §7 미결정 항목에 대한 인덱서 측 결정 | 열린 질문을 어떻게 확정하는가 |

가장 중요한 문서는 **03**(추출·reorg)과 **06**(계약 결정)이다. 03은 정확성의 근간이고, 06은 계약의 빈칸을 인덱서가 어떻게 메우는지를 정한다.

## 시스템 한 줄 정의

> 블록체인 노드에서 블록을 순차적으로 읽어, 각 트랜잭션을 **방향성 있는 자산 이동(BalanceDelta)** 으로 변환하고, **블록 높이 순서로·멱등하게·reorg 통지와 함께** Kafka로 발행하는 생산자.

## 상위 컨텍스트 — 인덱서의 위치

```
[블록체인 노드]  (Bitcoin Core RPC / Ethereum JSON-RPC / ...)
      │  fetch block
      ▼
┌──────────────────────────────────────────────┐
│           인덱서 (이 패키지)                     │
│  NodeClient → BlockFetcher → Extractor(어댑터)  │
│  → ReorgDetector → DeltaPublisher              │
│  (내부 상태: blocks / cursor / prevout 캐시)     │
└──────────────────────────────────────────────┘
      │  publish (계약 준수)
      ▼
   Kafka topic: balance-deltas
      │
      ▼
[클러스터링 시스템]  (완성됨, 이 인덱서의 소비자)
```

## 고정된 것 vs 설계할 것

**고정(계약이 정함, 바꿀 수 없음)** — 상세는 02 §출력 계약, 근거는 계약 문서:
- 전송은 Kafka, topic은 `balance-deltas`(환경변수).
- BalanceDelta와 reorg 이벤트가 **같은 topic**을 공유하고 `type` 필드로 구분.
- 메시지 스키마의 필수 필드와 타입. 특히 **`amount`는 반드시 문자열**(uint256 정밀도, 02 §강제 제약).
- `(chain_id, txid, delta_index)`가 멱등 키 — `delta_index`는 한 txid 안에서 유일.
- `chain_id`는 클러스터링 쪽 레지스트리에 등록된 값과 **정확히 일치**(대소문자 포함).
- 계정 체인 컨트랙트 배포는 `meta.contract_creation: true` 컨벤션.

**설계(이 패키지가 정함)**:
- 노드 접근·블록 페칭·체인별 추출 로직.
- reorg 감지 알고리즘과 통지.
- 내부 상태 저장(blocks·cursor·prevout 캐시).
- 순서 보장·멱등 발행 전략.
- 계약 §7 미결정 항목의 인덱서 측 결정(06).

## 계약 §7 미결정 항목 — 이 패키지에서의 처리

계약 문서 §7이 "인덱서 팀과 협의 필요"로 남긴 7개 항목은 대부분 **생산자(인덱서)의 책임 영역**이다. 06에서 각각에 대한 결정과 근거를 제시한다. 요약:

| 계약 §7 항목 | 인덱서 측 결정(06 상세) |
|---|---|
| 직렬화 포맷 | v1은 JSON(계약과 동일), 스키마 레지스트리 전환 경로 설계 |
| 토큰 식별자 부재 | `meta.token_contract` 컨벤션을 인덱서가 채워 발행(협의 제안) |
| 주소 정규화 책임 | **인덱서가 정규화**해서 발행(소스에서 처리) |
| 순서 보장 | 인덱서가 **블록 높이 오름차순** 발행, 파티션 키 = `chain_id` |
| reorg 감지 | 인덱서가 **권위 있는 감지자**, parent_hash 체인으로 감지·통지 |
| 파티셔닝/배치/백필 | 파티션 키 `chain_id`, 백필도 동일 순서 보장 |
| 인증/네트워크 | 운영은 SASL/TLS, 로컬은 평문 |

## 용어집

- **BalanceDelta**: 인덱서의 출력 원자 단위. `(chain_id, txid, delta_index, address, amount±, kind, block_height, block_hash, meta)`. 부호 있는 자산 이동.
- **prevout(이전 출력)**: UTXO 체인에서 input이 참조하는 이전 트랜잭션의 output. 소유 주소·금액을 알려면 되짚어야 함.
- **reorg**: 저장했던 블록 일부가 더 무거운 체인으로 교체되어 무효화되는 사건. 인덱서가 감지·통지한다.
- **finality_depth**: 몇 블록 뒤를 "확정"으로 볼지. 체인별로 다름(계약 §6).
- **커서(cursor)**: 인덱서가 마지막으로 처리·발행한 블록 높이.
- **멱등(idempotent)**: 같은 블록을 재처리해도 동일한 `(chain_id, txid, delta_index)` 키를 만들어, 소비자가 중복을 제거할 수 있게 하는 성질.

## 스택에 대하여

로직·인터페이스는 **스택 비종속**으로 기술한다(의사코드·인터페이스 계약). 언어·DB·라이브러리는 구현자가 선택한다. 다만 두 개의 외부 의존은 고정이다: (1) Kafka 발행(계약), (2) 대상 체인의 노드 RPC. 클러스터링 시스템이 Go·PostgreSQL·Kafka 생태계로 구현되어 있으므로 인덱서도 동일 생태계로 맞추면 운영·인증·직렬화 정합이 쉬워지지만, 필수는 아니다(04 §스택 요구 능력 참고).
