# 01. 기능 명세서 (Functional Specification)

> 인덱서가 **무엇을** 하는지 정의한다. 요구사항은 검증 가능한 단위로 기술하고 식별자(FR-n / NFR-n)를 부여해 05의 인수 기준과 연결한다. 출력 형식은 계약(문서 08)이 고정하므로, 여기서는 그 계약을 **준수해야 할 요구사항**으로 편입한다.

---

## 1. 범위 (Scope)

블록체인 노드에서 블록을 순차 인덱싱하여 BalanceDelta를 추출하고, reorg를 감지하며, 그 결과를 Kafka로 발행하는 **생산자 시스템**.

### 1.1 만들 것
- 체인별 노드 접근(RPC)과 블록/트랜잭션 페칭.
- 체인별 BalanceDelta 추출(UTXO: vin/vout 펼치기 + prevout 조회, 계정: native + ERC-20 로그 + 컨트랙트 배포 식별).
- 주소 정규화(소스에서 수행, 06 §3).
- reorg 감지와 통지(parent_hash 체인 검증).
- 내부 상태 관리(blocks·cursor·prevout 캐시).
- Kafka 발행(계약 준수: 순서·멱등·`type` 구분).
- 백필(과거 블록 일괄 적재)과 실시간 팔로우.

### 1.2 안 만들 것 (비범위)
- **클러스터링·라벨링·전처리·조회**: 전부 소비자(클러스터링 시스템)의 몫. 인덱서는 BalanceDelta 생산까지만.
- **잔액 계산·집계**: 인덱서는 delta를 내보낼 뿐, 주소 잔액을 확정하지 않는다.
- **가격·환율.**
- **스마트컨트랙트 내부 상태 해석**(토큰 잔액 매핑 등): ERC-20 Transfer 이벤트 관찰까지만.

---

## 2. 액터

- **블록체인 노드**: 블록 데이터의 원천(RPC).
- **Kafka**: 발행 대상 메시지 버스.
- **클러스터링 시스템**: BalanceDelta·reorg 이벤트의 소비자(계약 준수 대상).
- **운영자**: 체인 추가, 백필 시작, 노드 엔드포인트·인증 설정.

---

## 3. 기능 요구사항 (Functional Requirements)

### 3.1 페칭·순차 처리
- **FR-1** 인덱서는 대상 체인의 최신 높이를 조회하고, 커서 다음 블록부터 순차적으로 페칭한다.
- **FR-2** 인덱서는 블록을 **높이 오름차순**으로 처리·발행한다(계약 §7-4 순서 보장의 생산자 측 이행).
- **FR-3** 백필 모드에서 지정 구간(from~to)을 순서대로 일괄 처리하며, 실시간 모드와 동일한 순서·멱등 보장을 유지한다.

### 3.2 추출 (BalanceDelta 생성)
- **FR-4** **UTXO 체인**: 각 트랜잭션의 input(지출)과 output(수취)을 BalanceDelta로 펼친다. input의 소유 주소·금액은 prevout 조회로 확보한다. coinbase input은 지출 delta를 만들지 않는다.
- **FR-5** **계정 체인**: native 전송(from/to value)과 ERC-20 `Transfer` 로그를 BalanceDelta로 변환한다. `receipt.status == 0`(revert)인 트랜잭션은 delta를 만들지 않는다.
- **FR-6** 계정 체인 **컨트랙트 배포**는 생성된 컨트랙트 주소의 delta에 `meta.contract_creation: true`를 실어 발행한다(계약 §5 컨벤션).
- **FR-7** ERC-20 delta에는 **어떤 토큰인지**를 식별하는 `meta.token_contract`(토큰 컨트랙트 주소)를 채워 발행한다(계약 §7-2 해소, 06 §2).
- **FR-8** 한 트랜잭션에서 생성되는 모든 delta는 `delta_index`가 **그 txid 안에서 유일**해야 한다(계약 멱등 키).
- **FR-9** `amount`는 최소 단위(satoshi/wei 등) 부호 있는 정수를 **문자열로 인코딩**해 발행한다. JSON number 사용 금지(계약 §4 강제 제약).

### 3.3 주소 정규화
- **FR-10** 인덱서는 발행 전에 주소를 체인별 규칙으로 정규화한다(EVM 소문자, Bitcoin 표준 인코딩 등). 정규화 규칙은 06 §3. 주소를 추출할 수 없는 output(예: OP_RETURN)은 계약과 합의된 표기(`unparsed:...` 또는 발행 제외)로 처리한다(06 §3).

### 3.4 reorg 감지·통지
- **FR-11** 인덱서는 각 신규 블록의 `parent_hash`가 저장된 직전 블록 해시와 일치하는지 검증한다. 불일치 시 reorg로 판정한다.
- **FR-12** reorg 발생 시 공통 조상까지 되감아, 롤백된 블록 해시 목록을 담은 **reorg 이벤트**를 발행한다(계약 §3.2). 이어서 새 체인의 블록을 공통 조상+1부터 재추출·재발행한다.
- **FR-13** reorg 이벤트와 BalanceDelta 이벤트는 **같은 topic**에 발행하며 `type` 필드로 구분한다(계약 §2).

### 3.5 발행·멱등
- **FR-14** 발행은 파티션 키 `chain_id`로 하여 체인 내 순서를 보존한다(계약 §7-6, 06 §4).
- **FR-15** 재처리·재발행이 동일한 `(chain_id, txid, delta_index)` 키를 만들어, 소비자가 중복을 제거할 수 있어야 한다(멱등).
- **FR-16** 발행 실패·부분 실패 시 커서를 진전시키지 않는다. 다음 시도에서 같은 블록을 재처리(멱등이므로 안전)한다.

### 3.6 상태 관리
- **FR-17** 인덱서는 처리한 블록을 `(chain_id, height, hash, parent_hash)`로 저장한다(reorg 감지 근거).
- **FR-18** 인덱서는 체인별 커서(마지막 발행 높이)를 저장한다.
- **FR-19** UTXO 체인의 prevout 조회를 위해 `-txindex` 노드 또는 자체 prevout/UTXO 캐시를 사용한다. reorg 시 캐시도 함께 롤백한다(03 §prevout).

### 3.7 운영
- **FR-20** 운영자는 새 체인을 노드 엔드포인트·모델타입·finality_depth와 함께 등록할 수 있다(04 §어댑터).
- **FR-21** 노드/네트워크 오류는 지수 백오프로 재시도한다.

## 4. 비기능 요구사항 (Non-functional Requirements)

- **NFR-1 정확성**: 추출된 delta는 온체인 사실과 일치해야 한다. revert된 트랜잭션의 delta를 발행하지 않는다(FR-5).
- **NFR-2 멱등·결정성**: 같은 블록 재처리는 동일 메시지 키 집합을 생성한다.
- **NFR-3 순서성**: 체인 내에서 블록 높이 오름차순 발행이 보장된다.
- **NFR-4 정밀도 무손실**: uint256 금액이 문자열 인코딩으로 손실 없이 전달된다(FR-9).
- **NFR-5 회복성**: 노드 지연·발행 실패에서 커서 기반으로 안전하게 재개된다.
- **NFR-6 확장성**: 새 체인 추가가 어댑터 구현 + 설정으로 끝난다(코어 불변, 04 §확장).
- **NFR-7 관찰성**: 인덱싱 지연(노드 최신 높이 − 커서), reorg 빈도·깊이, 발행 실패율을 지표로 노출한다.
- **NFR-8 스택 비종속성**: 로직·인터페이스는 특정 스택 가정 없이 구현 가능해야 한다(외부 의존은 Kafka·노드 RPC뿐).

## 5. 계약 준수 요구사항 (요약, 상세는 02·06)

인덱서는 다음을 반드시 지킨다. 위반은 소비자(클러스터링) 정합성을 깨뜨리는 결함이다.

- 메시지 스키마·필드 타입 준수(02 §출력 계약).
- `amount` 문자열 인코딩(FR-9).
- `(chain_id, txid, delta_index)` 멱등 키, `delta_index` txid 내 유일(FR-8).
- `chain_id` 정확 일치(대소문자 포함).
- `block_hash` 항상 포함(reorg 롤백의 유일 근거).
- 컨트랙트 배포 `meta.contract_creation`(FR-6), 토큰 식별 `meta.token_contract`(FR-7).
- reorg 이벤트 발행(FR-12), 같은 topic·`type` 구분(FR-13).
