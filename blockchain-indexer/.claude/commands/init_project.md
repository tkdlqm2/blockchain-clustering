# init_project — 프로젝트 초기 세팅 인터뷰 & 스캐폴딩

대상 경로: $ARGUMENTS (미지정 시 현재 디렉토리)

> 이 커맨드는 **질문 → 생성**의 두 단계로 동작한다. 절대 순서를 건너뛰지 않는다: 먼저 STEP 1~6을 통해 필요한 정보를 전부 모으고, STEP 7에서만 실제 파일을 생성한다.
> 고정된 체크리스트를 기계적으로 다 묻지 않는다. 이 프로젝트의 성격(도메인, 규모, 팀 상황)에 맞춰 **무엇을 더 물어야 완성도 있게 만들 수 있을지 능동적으로 판단해서 질문을 추가**하는 것이 이 커맨드의 핵심이다.
> 구조화된 선택지(언어, DB 종류, 인프라 범위 등)는 `AskUserQuestion`으로 묻고, 서비스 설명·도메인·API 명세처럼 자유 서술이 필요한 것은 대화로 자연스럽게 받는다.

---

## 진행 전 확인

- 대상 경로에 이미 파일이 있는지 확인한다(`ls`, `git status`). 비어있지 않다면 어떤 파일이 있는지 보여주고, 덮어써도 되는지 사용자에게 먼저 확인한다 — 조용히 덮어쓰지 않는다.
- 이 커맨드는 여러 턴에 걸쳐 진행되는 대화형 흐름이다. 한 번에 모든 걸 몰아서 묻지 말고, 섹션 단위로 나눠서 자연스럽게 진행한다.

---

## STEP 1 — 기술스택

1. **언어/런타임**: 어떤 언어로 구현하는가(Go/Java·Kotlin/Node·TypeScript/Python/기타). 프레임워크가 있다면 함께(Spring Boot, Express/NestJS, FastAPI, Gin/Echo 등).
2. **DB**: 사용할 DB 종류와 버전(PostgreSQL/MySQL/MongoDB/기타/없음). 여러 개면 각각의 용도(주 저장소 vs 조회 전용 등).
3. **그 외 구성요소**: 메시지 큐(Kafka/RabbitMQ/SQS/없음), 인메모리 캐시·구조(Redis/Memcached/없음), 검색엔진(Elasticsearch 등), 기타 이 프로젝트에 필요한 미들웨어.

언어/프레임워크 선택에 따라 자연스럽게 따라오는 후속 질문이 있으면 이어서 묻는다(예: Go라면 ORM 쓸지 raw SQL 쓸지, Java/Kotlin이면 Spring Boot 버전과 JPA 사용 여부).

---

## STEP 2 — 인프라 (docker-compose)

1. **적용 범위**: STEP 1에서 고른 DB/캐시/브로커 중 docker-compose로 로컬 기동할 대상을 확정한다(기본은 전부 포함, 제외하고 싶은 게 있으면 확인).
2. **버전/포트/볼륨**: 각 서비스의 이미지 버전, 호스트 포트 매핑, 데이터 영속화(볼륨) 필요 여부.
3. **인프라 자격증명 생성**: DB app user, Redis user(ACL 사용 시) 등 실제 자격증명을 생성한다.
   - `openssl rand -base64 24` 등으로 실제 랜덤 비밀번호를 생성한다(추측 가능한 기본값 사용 금지).
   - 생성된 값은 `.env`(gitignore 대상)에만 기록하고, `.env.example`에는 placeholder만 남긴다.
   - DB는 superuser/root와 별도로 **애플리케이션 전용 유저**를 만드는 것을 기본으로 한다(최소 권한 원칙).
4. **기동 순서/헬스체크**: 서비스 간 `depends_on` + healthcheck 조건을 확인한다(앱이 DB보다 먼저 뜨지 않도록).

---

## STEP 3 — 설정(config)/환경변수 체계

1. config 파일 형식과 위치 관례를 정한다(예: `configs/config.yaml` + `${VAR}` 치환, 또는 순수 환경변수만 사용).
2. 환경별 분리가 필요한가(dev/staging/prod), 필요하다면 어떻게 구분할지(파일 분리 vs 환경변수 프로파일).
3. 실제 운영 환경에서의 시크릿 관리 방식(로컬은 `.env`로 충분하지만, 배포 시 Vault/SSM/K8s Secret 등 무엇을 쓸지) — 지금 당장 구현할 필요는 없어도 CLAUDE.md에 남길 방향성 정도는 확인한다.

---

## STEP 4 — 서비스 설명 & 도메인

1. **서비스 설명**: 이 서비스가 하는 일을 한두 문단으로.
2. **서비스 도메인**: 핵심 도메인 개념, 바운디드 컨텍스트(있다면), 이 서비스가 전체 시스템에서 어디에 위치하는가(다른 서비스와의 관계, 상류/하류).

---

## STEP 5 — 외부 통신 서비스

1. 이 서비스가 호출하거나(outbound) 요청을 받는(inbound) 외부 서비스 목록을 확인한다.
2. **각 통신에 대해 명세서를 공유해달라고 적극적으로 요청한다** — OpenAPI/Swagger, `.proto`, AsyncAPI, 또는 요청/응답 예시(curl, JSON 샘플)라도 요청한다. "대충 이런 API일 것"이라고 추측해서 넘어가지 않는다.
3. 명세서가 아직 없다면: 이 프로젝트에서 직접 설계해야 하는지, 상대 팀이 줄 예정인지 확인하고, 없다는 사실 자체를 CLAUDE.md/README에 TODO로 남긴다.

---

## STEP 6 — 완성도를 위한 동적 추가 질문 (생략 금지)

지금까지의 답변을 근거로, **이 프로젝트를 실제로 완성도 있게 구현하려면 무엇을 더 물어야 하는지 스스로 판단**해서 질문한다. 아래는 판단에 참고할 트리거 목록이지, 전부 순서대로 물어야 하는 고정 체크리스트가 아니다 — 이 프로젝트에 실제로 해당하는 것만 고른다.

- **인증/인가 방식**: OAuth2/JWT/세션 중 무엇을 쓰는가, 인증 주체가 사용자인지 서비스 간(mTLS, API key)인지.
- **배포 대상**: AWS/GCP/온프레미스/단일 서버 등, 이에 따라 config·docker-compose 구성이 달라지는가.
- **팀 컨벤션**: 커밋 메시지 규칙, 브랜치 전략, 이미 정해진 게 있다면 CLAUDE.md에 반영.
- **테스트 전략**: 단위/통합/e2e 중 이 프로젝트에서 최소한 요구되는 수준.
- **로깅/모니터링**: 구조화 로깅 여부, ELK/Datadog/CloudWatch 등 연동 계획.
- **CI/CD**: 파이프라인이 이미 있는지, 이 스캐폴딩 단계에서 뼈대(예: GitHub Actions 워크플로 파일)까지 필요한지.
- **트래픽 규모 추정**: 초당 요청 수, 동시 사용자 수 등 — 인프라 사이징(커넥션 풀 크기, 캐시 필요 여부)에 직접 영향.
- **규제/컴플라이언스 요구사항**: 결제·금융·의료·개인정보 도메인이면 특히 — PCI-DSS, 개인정보보호법, 멱등성·감사로그 요구사항.
- **다국어/타임존**: 여러 지역 대상 서비스인가.

사이드 프로젝트/프로토타입처럼 성격이 가벼우면 대부분 생략하고 핵심만 확인한다. 금융/결제/의료처럼 무거운 도메인이면 규제·정합성 관련 질문 비중을 높인다.

---

## STEP 7 — 산출물 생성 (스캐폴딩)

STEP 1~6에서 모은 답변을 바탕으로 아래를 생성한다. 실제 파일을 쓰기 전에 무엇을 만들지 요약해서 한 번 보여주고 진행한다.

1. **디렉토리 구조**: 선택된 언어/프레임워크 관례에 맞는 최소한의 골격(과도한 보일러플레이트 금지 — 실제로 필요한 만큼만).
2. **`docker-compose.yml`**: STEP 2에서 확정한 서비스만 포함, 자격증명은 환경변수(`${DB_APP_PASSWORD}` 등)로 참조, healthcheck와 `depends_on: condition: service_healthy` 포함.
3. **`.env`**(실제 생성된 개발용 시크릿, git에 커밋되지 않도록 `.gitignore`에 추가 확인/추가) + **`.env.example`**(placeholder만).
4. **config 파일**: STEP 3에서 정한 형식/위치대로.
5. **`CLAUDE.md`**: 서비스 설명, 도메인, 기술스택, 외부 통신 목록(명세서 위치 링크 포함), 그리고 STEP 6 답변 중 "절대 어기면 안 되는 것"에 해당할 만한 항목(도메인 특성상 나온 규제·정합성 요구사항 등)을 초안으로. 코드로 알 수 있는 내용은 쓰지 않는다(이전에 만든 CLAUDE.md들과 같은 원칙).
6. **`README.md`** 스켈레톤: 개요, 기술스택, 로컬 실행 방법(`docker compose up` + 앱 실행).
7. 외부 통신 명세서를 받았다면 `docs/api/` 등 적절한 위치에 원본을 저장하고 CLAUDE.md에서 링크.

생성 후 `docker compose config`로 `docker-compose.yml` 문법을 검증한다(`docker compose up`처럼 실제로 컨테이너를 띄우는 명령은 포트 점유 등 부작용이 있으므로 사용자 승인 없이 실행하지 않는다).

## 안전 수칙 (Do / Do-Not)

- **DO**: 기존 파일을 덮어쓰기 전 반드시 확인받는다.
- **DO**: 생성된 시크릿이 `.gitignore`에 걸려 있는지 `git check-ignore`로 확인한다.
- **DO**: 사용자가 준 API 명세서/설명을 그대로 반영한다 — 없는 정보는 추측으로 채우지 않고 TODO로 남긴다.
- **DO-NOT**: `docker compose up`처럼 실제로 리소스를 점유/실행하는 명령을 사용자 승인 없이 실행하지 않는다.
- **DO-NOT**: 추측 가능한 기본 비밀번호(`password123` 등)를 생성하지 않는다 — 항상 실제 랜덤 값을 생성한다.
- **DO-NOT**: STEP 1~6을 건너뛰고 바로 스캐폴딩부터 하지 않는다.
