# security_review — 보안 리뷰 렌즈

점검 대상: $ARGUMENTS

> 이 커맨드는 다른 리뷰 커맨드들과 성격이 다르다 — 성능/설계 품질이 아니라 **공격 가능 여부**를 본다.
> SQL/커맨드 인젝션은 `validation_review`가 단독 소유한다(중복 방지) — 여기서는 인증/인가(IDOR 포함), 시크릿 관리, 민감정보 로깅, rate limiting만 본다.
> "먼저 이 프로젝트의 인증/인가 메커니즘과 민감 데이터 경로를 찾고(STEP 1) → 발견된 것에만 해당 항목을 적용(STEP 2)"하는 순서를 반드시 지킨다.
> 사용법: `security_review [선택: 경로 또는 엔드포인트 이름]`
> - 인자 없음 → 프로젝트 전체 스캔
> - 인자 있음 → 해당 경로/엔드포인트로 범위 한정

---

## 범위 (Scope)

- **대상**: 인증(Authentication) 메커니즘과 우회 가능성, 인가(Authorization) 검사 누락 — 특히 **IDOR**(다른 사용자의 리소스 ID로 접근), 시크릿(API 키/비밀번호/인증서) 하드코딩, 로그에 남는 민감정보, rate limiting(자체 엔드포인트를 남용으로부터 보호).
- **제외**: SQL/커맨드 인젝션 및 입력 검증 전반(→ `validation_review`, 단독 소유), API 계약/버전(→ `api_review`), 예외 처리·에러 매핑(→ `error_review`), 레이어 경계(→ `arch_review`), DB 쿼리 성능(→ `db_review`), 외부 통신 신뢰성(→ `comm_review`), 동시성(→ `concurrency_review`), 다중 리소스 정합성(→ `consistency_review`). 이 항목이 나오면 "범위 밖, 해당 커맨드로"라고만 표시하고 리뷰하지 않는다.

---

## STEP 1 — 대상 인벤토리 (Discovery) · 반드시 먼저

코드베이스를 스캔해 **실제로 존재하는 인증/인가/시크릿/로깅 경로만** 목록화한다. 없는 것은 리뷰하지 않는다.

탐지 신호:

| 종류 | 탐지 신호(예시) |
|------|----------------|
| 인증 | JWT/세션 검증 미들웨어, `@Authenticated`/`@RequireAuth`, API key 검사, OAuth 콜백 |
| 인가 | role/permission 체크(`@PreAuthorize`, `@RequireRole`), 소유권 검사(`resource.userId == currentUser.id`) |
| IDOR 후보 | path/query 파라미터의 ID로 직접 DB를 조회하는 엔드포인트(`/orders/{id}`, `/users/{id}/...`) |
| 시크릿 | 문자열 리터럴로 보이는 API 키/비밀번호/토큰, `.env`/설정 파일의 평문 값, 인증서 개인키 파일 |
| 로깅 | `log.info/debug/error` 호출에 요청 바디·헤더·사용자 객체 전체를 그대로 넘기는 코드 |
| Rate limiting | rate limiter 미들웨어, 토큰 버킷/슬라이딩 윈도우 라이브러리, 로그인·재설정 엔드포인트의 시도 횟수 제한 |

**STEP 1 출력**: 발견된 항목의 표를 먼저 제시한다.

| # | 엔드포인트/컴포넌트 | 종류(인증/인가/시크릿/로깅/rate-limit) | 파일:라인 |
|---|----------------------|------------------------------------------|-----------|

- 하나도 못 찾으면: 리뷰를 만들지 말고 "인증/인가 관련 코드를 찾지 못함. 있는데 못 찾았다면 경로를 알려달라"고 **한 번만** 묻는다.
- 인증이 필요한지 공개 엔드포인트인지 애매한 경우만 모아서 함께 확인한다.

---

## STEP 2 — 대상별 점검 (발견된 종류에만 적용)

### A. 인증 (Authentication)
- 인증이 필요한 엔드포인트 전체에 실제로 인증 검사가 걸려 있는가 — 하나라도 빠진 엔드포인트가 있는가.
- 토큰 검증이 서명·만료·발급자를 제대로 확인하는가(예: 알고리즘을 클라이언트가 지정하게 허용, 서명 검증 스킵 등 명백한 결함).
- 인증을 우회할 수 있는 경로(디버그/내부 전용이라 착각한 엔드포인트, 헬스체크로 위장한 데이터 엔드포인트)가 있는가.

### B. 인가 (Authorization) / IDOR
- 인증만 확인하고 **인가**(이 사용자가 이 리소스에 접근할 권한이 있는지)는 확인하지 않는 엔드포인트가 있는가.
- **IDOR**: 요청 파라미터의 리소스 ID로 DB를 조회할 때, 조회된 리소스가 현재 사용자 소유이거나 접근 가능한지 검증하는 코드가 있는가 — 없다면 다른 사용자의 ID를 넣어 접근 가능한 취약점.
- 관리자 전용 기능이 프론트엔드에서만 숨겨져 있고 백엔드에서 role 검증이 없는가.

### C. 시크릿 관리
- 소스 코드/설정 파일에 하드코딩된 API 키, 비밀번호, 토큰, 개인키가 있는가.
- 시크릿이 환경변수 또는 시크릿 매니저(Vault, SSM 등)로 주입되는가.
- `.env` 등 민감 파일이 `.gitignore`에 포함되어 있는가, 과거 커밋에 이미 유출된 흔적이 있는가(git 이력에서 확인 가능한 범위 내).

### D. 민감정보 로깅
- 비밀번호, 토큰, 카드번호, 주민번호 등이 로그에 평문으로 남는가.
- 에러 로그/스택트레이스에 요청 바디 전체를 무분별하게 찍는 코드가 있는가.

### E. Rate Limiting (있을 때만; 없다면 필요성만 언급)
- 로그인, 비밀번호 재설정, OTP 검증 등 브루트포스에 취약한 엔드포인트에 시도 횟수 제한이 있는가.
- 공개 API 전반에 남용 방지 장치(IP/계정 단위 rate limit)가 있는가.

---

## STEP 3 — 출력 포맷 (일정하게)

각 발견은 아래 형식으로. 심각도 순(Critical→Low)으로 정렬한다.

```
[심각도] <한 줄 요약>
  대상 : <엔드포인트/컴포넌트>
  위치 : <파일:라인>
  근거 : <왜 공격 가능한가 — STEP 2의 어떤 항목 위반인지, 가능하면 공격 시나리오 한 줄>
  수정안: <구체적 조치 — 코드 수준>
```

**심각도 기준**
- `Critical`: 인증/인가 완전 누락으로 임의 사용자가 타인 데이터에 접근·변조 가능(IDOR 포함), 하드코딩된 프로덕션 시크릿, 로그에 평문 비밀번호/토큰.
- `High`: 관리자 기능의 백엔드 인가 미검증, 브루트포스 가능한 로그인/재설정 엔드포인트에 rate limit 없음.
- `Medium`: 시크릿 관리 방식 개선 필요(환경변수는 쓰지만 로테이션·매니저 없음), 로그에 부분적 민감정보.
- `Low`: 방어 심화 권장(추가 rate limit, 로깅 마스킹 개선).

**마지막 요약 표** — 엔드포인트/컴포넌트 × 점검 상태:

| 엔드포인트 | 인증 | 인가/IDOR | 시크릿 | 로깅 | rate-limit | 비고 |
|-----------|------|-----------|--------|------|------------|------|
| GET /orders/{id} | ✅ | ❌ | - | - | - | 소유권 검증 없음(IDOR) |

그리고 심각도별 개수 한 줄: `Critical 1 · High 0 · Medium 0 · Low 0`.

## 규칙 (Do / Do-Not)

- **DO**: STEP 1에서 찾은 항목만 리뷰한다. 실제 `파일:라인`을 인용한다. 위치를 못 찾으면 "확인 불가"로 표시하고 지어내지 않는다.
- **DO**: 잘 방어된 경로도 요약 표에 ✅로 반영한다(문제만 나열하지 않음).
- **DO-NOT**: SQL/커맨드 인젝션을 여기서 다루지 않는다 — `validation_review`가 단독 소유(중복 리포트 금지).
- **DO-NOT**: API 계약, 예외 처리, 레이어 경계, DB/통신/동시성/정합성 문제를 여기서 다루지 않는다(각각 해당 커맨드로).
- **DO-NOT**: 근거 없는 추측성 지적을 하지 않는다. 공격 시나리오는 실제 코드 경로에 근거해서만 서술한다.

## CLAUDE.md 연계

- 인증/인가는 대개 미들웨어/프레임워크 계층에 위치한다. 도메인 로직 안에 인가 체크가 하드코딩되어 있거나, 반대로 인가 체크가 아예 도메인에 없이 컨트롤러 산발적으로만 존재하면 `arch_review` 병행 검토 대상이다.
- 새 엔드포인트 추가 직후 이 커맨드로 점검하면, 완료 정의를 만족하기 전에 인가 검사 누락을 걸러낼 수 있다.
