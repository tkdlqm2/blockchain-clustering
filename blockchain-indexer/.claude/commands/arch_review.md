# arch_review — 아키텍처 경계 리뷰 렌즈

점검 대상: $ARGUMENTS

> 이 커맨드는 **현재 프로젝트가 실제로 채택한 아키텍처 스타일과 그 경계**만 대상으로 리뷰한다.
> "이상적인 클린 아키텍처"를 기준으로 삼지 않는다. "먼저 이 프로젝트가 실제로 어떤 레이어/경계를 쓰는지 찾고(STEP 1) → 그 경계에 대한 위반만 점검(STEP 2)"하는 순서를 반드시 지킨다.
> 사용법: `arch_review [선택: 경로 또는 모듈 이름]`
> - 인자 없음 → 프로젝트 전체 스캔
> - 인자 있음 → 해당 경로/모듈로 범위 한정

---

## 범위 (Scope)

- **대상**: 레이어 간 의존성 방향(domain ↔ application ↔ infrastructure ↔ presentation 등), 모듈/패키지 경계, 포트-어댑터 분리, 애그리거트 경계, 순환 의존.
- **제외**: DB 쿼리 성능(→ `db_review`), 외부 통신 세부(→ `comm_review`), 프로세스 내 동시성(→ `concurrency_review`), 다중 리소스 정합성(→ `consistency_review`), 예외 처리 방식(→ `error_review`), API 계약 설계(→ `api_review`), 입력 검증 존재 여부(→ `validation_review`), 인증/인가·시크릿·rate limiting(→ `security_review`). 이 항목이 나오면 "범위 밖, 해당 커맨드로"라고만 표시하고 리뷰하지 않는다.

---

## STEP 1 — 아키텍처 인벤토리 (Discovery) · 반드시 먼저

코드베이스와 문서를 스캔해 **이 프로젝트가 실제로 따르는 구조**를 먼저 파악한다. 존재가 확인되지 않은 규칙은 적용하지 않는다.

탐지 신호:

| 확인 항목 | 탐지 신호(예시) |
|-----------|----------------|
| 레이어 구조 | 디렉토리명(`domain`/`application`/`usecase`/`infrastructure`/`adapter`/`presentation`/`controller`/`repository`/`service`) |
| 아키텍처 스타일 힌트 | 포트-어댑터(인터페이스가 안쪽, 구현체가 바깥쪽), MVC(controller-service-repository), 모듈형 모놀리스(도메인별 최상위 디렉토리) |
| 문서화된 규칙 | `CLAUDE.md`, `README.md`, `docs/adr/*`, 아키텍처 다이어그램·의존성 규칙 명시 여부 |
| 모듈/패키지 경계 | 모노레포의 워크스페이스 구성(`go.mod`의 여러 모듈, 멀티모듈 빌드 설정 등), 명시적 의존 허용 규칙 |
| DDD 요소 | 애그리거트 루트, 엔티티, 값 객체, 리포지토리 인터페이스 위치 |

**STEP 1 출력**: 이 프로젝트가 실제로 쓰는 구조를 먼저 요약한다.

```
탐지된 아키텍처 스타일: <예: 레이어드(계층형) / 포트-어댑터 / MVC / 모듈형 모놀리스 / 특정 스타일 불명확>
레이어·모듈 목록:
  - <레이어/모듈명>: <디렉토리 경로> — <역할 추정>
  - ...
문서화된 규칙: <있으면 파일:라인 인용, 없으면 "명시적 문서 없음, 디렉토리 구조로만 추정">
```

- 레이어/모듈 구분이 사실상 없는 단일 패키지·스크립트성 프로젝트라면: 리뷰를 만들지 말고 "레이어 구조를 찾지 못함. 특정 아키텍처 규칙을 따르고 있다면 알려달라"고 **한 번만** 묻는다.
- 구조는 있지만 규칙이 문서화되어 있지 않다면: 디렉토리 구조에서 관찰되는 **암묵적 규칙**(예: “infrastructure가 domain을 참조하지 않는 것으로 보임”)을 가설로 명시하고, 그 가설을 기준으로 위반만 점검한다(추측임을 표시).

---

## STEP 2 — 대상별 점검 (발견된 구조에만 적용)

STEP 1에서 확인된 스타일에 해당하는 항목만 본다. 채택하지 않은 스타일의 규칙(예: 포트-어댑터를 안 쓰는데 "포트 분리 안 됨"이라고 지적)은 만들어내지 않는다.

### A. 공통 (레이어/모듈 구분이 있을 때)
- **의존성 방향**: 안쪽(도메인/코어)이 바깥쪽(인프라/프레임워크)을 참조하지 않는가 — 역방향 import가 있는지 실제 코드에서 확인.
- **프레임워크 누수**: 도메인 계층에 HTTP/gRPC/ORM 애노테이션·클라이언트 라이브러리가 직접 등장하는가.
- **순환 의존**: 레이어/모듈 간 순환 import가 있는가.
- **책임 집중(God object/fat layer)**: 한 파일·클래스가 여러 레이어의 책임(예: HTTP 파싱 + 비즈니스 로직 + DB 접근)을 동시에 갖는가.
- **인터페이스-구현 분리**: 포트-어댑터 스타일이라면, 인터페이스가 안쪽(도메인/애플리케이션)에 있고 구현체만 바깥쪽(인프라)에 있는가.

### B. DDD 요소 (애그리거트/엔티티 개념이 있을 때만)
- 한 애그리거트가 다른 애그리거트를 **객체 참조**로 직접 물고 있는가, 아니면 ID 참조로 느슨하게 연결되는가.
- 애그리거트 루트를 거치지 않고 외부에서 내부 엔티티를 직접 변경하는 경로가 있는가.
- 값 객체가 불변으로 설계되어 있는가.
- **컨텍스트 간 직접 참조**: 서로 다른 바운디드 컨텍스트/도메인 모듈이 공용 API·이벤트·published language를 거치지 않고 서로의 내부 구현(엔티티, 리포지토리 등)을 직접 import하는가 — 한 컨텍스트의 내부 변경이 다른 컨텍스트를 깨는 결합이 있는가.

### C. 계층형 MVC (Controller-Service-Repository 스타일일 때만)
- 컨트롤러에 비즈니스 로직이 새어있는가(fat controller).
- 리포지토리 인터페이스 정의와 구현체의 위치가 분리되어 있는가.
- 트랜잭션 경계 관리 책임이 어느 계층에 있는지 일관적인가.

### D. 모듈/패키지 경계 (모노레포·멀티모듈일 때만)
- 빌드 설정(워크스페이스, go.mod 등)에 정의된 허용 의존 방향과 실제 import가 일치하는가.
- 모듈 간 순환 의존이 있는가.

## STEP 3 — 출력 포맷 (일정하게)

각 발견은 아래 형식으로. 심각도 순(Critical→Low)으로 정렬한다.

```
[심각도] <한 줄 요약>
  대상 : <레이어/모듈 이름>
  위치 : <파일:라인>
  근거 : <왜 위반인가 — STEP 1에서 확인된 어떤 규칙/가설을 어겼는지>
  수정안: <구체적 조치 — 어디로 옮기고 어떻게 분리할지>
```

**심각도 기준**
- `Critical`: 도메인이 인프라/프레임워크에 직접 의존(테스트 불가·이식성 붕괴), 빌드를 막는 순환 의존.
- `High`: fat controller/service가 여러 레이어 책임을 겸함, 리포지토리 구현이 도메인에 누수.
- `Medium`: 인터페이스-구현 분리 불완전, 애그리거트 경계 모호.
- `Low`: 네이밍/디렉토리 구조 정리 권장.

**마지막 요약 표** — 레이어/모듈 × 점검 상태:

| 레이어/모듈 | 의존방향 | 프레임워크누수 | 순환의존 | 책임분리 | 비고 |
|------------|---------|----------------|---------|---------|------|
| domain | ✅ | ❌ | ✅ | ⚠️ | gRPC 클라이언트 직접 참조 |

그리고 심각도별 개수 한 줄: `Critical 1 · High 1 · Medium 0 · Low 0`.

## 규칙 (Do / Do-Not)

- **DO**: STEP 1에서 확인된 구조·규칙(문서화됐든 가설이든)에 대한 위반만 리뷰한다. 실제 `파일:라인`을 인용한다. 위치를 못 찾으면 "확인 불가"로 표시하고 지어내지 않는다.
- **DO**: 규칙이 잘 지켜진 레이어도 요약 표에 ✅로 반영한다(문제만 나열하지 않음).
- **DO-NOT**: 프로젝트가 채택하지 않은 아키텍처 스타일의 규칙을 기준으로 지적하지 않는다("클린 아키텍처는 원래 이래야 한다"는 이유만으로 지적 금지).
- **DO-NOT**: DB·외부 통신·동시성 세부 이슈를 여기서 다루지 않는다(각각 `db_review`·`comm_review`·`concurrency_review`로).
- **DO-NOT**: 근거 없는 추측성 지적을 하지 않는다.

## CLAUDE.md 연계

- 이 커맨드는 `db_review`/`comm_review`/`concurrency_review`/`consistency_review`/`error_review`/`api_review`/`validation_review`/`security_review`가 "도메인 계층에서 발견된 DB/통신/동시성/정합성/예외처리/계약/검증/인가 관련 코드"를 넘길 때의 착지점이다 — 다른 리뷰에서 레이어 위반으로 분류된 항목은 여기서 함께 정리한다.
- CLAUDE.md에 아키텍처 규칙(레이어 구조, 의존 방향)이 명시되어 있다면 STEP 1에서 반드시 그 문서를 우선 인용하고, 없다면 위와 같이 디렉토리 구조 기반 가설임을 명시한다.
